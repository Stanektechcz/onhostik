## Objective

Deleting a web hosting on ISPConfig takes the customer's data and their access with it, instead of deleting the
vhost and leaving the databases, logins, FTP and SSH accounts, cron jobs and further host names on a live node.

## Context

Audit row 98. `IspConfigWebProvider::terminate()` called `sites_web_domain_delete`, which deletes **one** row.
Everything else hangs off the site by `parent_domain_id` and is named nowhere in that call. The aaPanel adapter has
always removed its children itself (`dropCron`, `dropNodeProjects`, and `DeleteSite` with `path/database/ftp = 1`);
the ISPConfig one did not. Whether the panel tidies up behind the remote API is not something the platform may
assume — and even if it does, every delete here is idempotent and scoped to this site.

## Out of scope

- Existing services: nothing sweeps a node for what earlier terminations left there. The cleanup applies to
  terminations from here on. Finding the old leftovers is a staging query, recorded in the handoff.
- The ISPConfig **client account** when an organization's last site goes (limits live in `ClientAllowance`,
  TASK-0008); an empty client is not data and costs nothing.
- aaPanel: its adapter already does this.

## Contracts affected

- `InfrastructureProvider::terminate()` result `data` gains an optional `leftover` (kind → ids). No signature change.
- New event `service.purge.leftover` (operators only): `name`, `node`, `kinds[]`, `leftover`, and `after: migration`
  when it comes from the migration cleanup. Catalogued and routed.

## Acceptance criteria

- [x] A terminated site's databases, database logins, FTP accounts, shell users, cron jobs, alias and subdomain
      vhosts are gone from the panel.
- [x] Nothing of a neighbour can be reached: every listing is scoped by `parent_domain_id` to this site, and the
      existing domain/`system_user` guards still run first.
- [x] A database login is deleted only when it owns no database anywhere (a login shared with another site's
      database stays).
- [x] A refusal does not fail the termination but is named in `leftover` and published to the operators.
- [x] The same holds for the old node after a web migration.

## Security considerations

This is a data-retention and access finding: a shell user is a system account on a shared node and an FTP or
database login keeps working long after the customer is gone. Deliberate decisions:

1. **The termination is never failed by a child.** The customer is entitled to be rid of the service and the final
   archive (60 days, `finalArchiveStep`) is already taken; a stuck delete would hold a paid-off service open.
2. **Only this site's own children are in reach.** Every listing filters by `parent_domain_id`, the existing
   `terminate()` guards (domain matches, `system_user` matches) run before anything is deleted, and a shared
   database login is left alone.
