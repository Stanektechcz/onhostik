## Objective

Owner decision 7 of 2026-10-06: web hosting customers can order their own Penpot (open-source design tool), delivered and run by
the platform — with fakes only; no server is touched. The catalogue revision is prepared and not applied.

## Context

Phase H, package H8. Penpot self-host = Docker Compose (frontend, backend, exporter, PostgreSQL 15, Valkey). Facts taken from the
official docs and compose file (help.penpot.app/technical-guide, docker/images/docker-compose.yaml, backend/scripts/manage.py), see
`docs/runbooks/penpot.md` §"Facts from the official Penpot documentation".

## Decision: delivery model

One compose project per customer service on a **dedicated Penpot node** (provider `penpot`, node role `penpot`), reached over SSH
by the platform, behind Caddy (automatic HTTPS). Rejected: shared aaPanel/ISPConfig (Docker = root for every tenant, `www` cannot
exec on hardened aaPanel nodes, memory), one shared Penpot with teams (no isolation, no per-customer export/limits), VPS template
(customer would run a server; no cloud-init user-data in the adapter), Kubernetes Apps (draft, not operated). Reasons in the runbook.

## Security considerations

Secrets only in the vault and the node's `.env` (0600, written over SFTP); a test greps operations, attempts, audit, outbox,
provider_calls and idempotency keys for them. The owner password is passed once to the node and forgotten by OperationSecrets.
No customer shell on the node; the stack listens on 127.0.0.1 only; registration off. Open: no real SSO (no OIDC IdP in ONhost).
