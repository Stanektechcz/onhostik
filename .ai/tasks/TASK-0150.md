## Objective

The Penpot node can be built and registered as the runbook says, without harming a host that already runs other containers, and
the doctor tells the truth about a sandbox-only node. Six verified defects of TASK-0141/TASK-0123 are fixed or documented.

## Context

Verified bugs handed over by the coordinator (2026-10-08):

1. `infra/penpot/provision-node.sh` made `/etc/caddy/onhost-penpot` (and its placeholder) the property of `onhost` in step 3, but
   created the user only in step 4: the first real run would stop with `install: invalid user 'onhost'`.
2. On a host that already runs Docker (a Wings game node) the script wrote `/etc/docker/daemon.json` and **restarted Docker**
   (every game container without live-restore stops), pinned a Docker major with priority 1001, set `ufw default deny incoming`
   and enabled ufw (cuts Wings 8080/2022), and installed Caddy whose package starts at once with its default `:80` file server.
3. `ProvisioningController::upsertNode` allowed roles `compute,web,managed,game,mail,dns,apps,backup` — not `penpot`, which the
   service layer allows and the runbook's step 4 uses: the documented registration answered 422.
4. No way to drive a rootless Docker of the deploy user (the `docker` group is root on the host).
5. Staging: the deployer refuses Path B once any provider instance holds a stored secret (`path_b_stored_secrets`) — registering a
   Penpot node key makes staging Path A; the procedure was not written down.
6. Doctor: `PenpotHealth::usableNodes()` counted nodes of `options.sandbox` instances, which the scheduler gives to sandbox
   tenants only — "on sale; usable Penpot nodes: 1" while every customer order was refused (`penpot_unavailable`).

## Security considerations (self-check, .ai/SECURITY_RULES.md §1)

- **Command injection (adapter):** `docker_host` comes from staff-set instance options; it is allowed only as
  `^unix:///[A-Za-z0-9._/-]{1,200}$` without `..` segments and is still shell-quoted (`Q::arg`). A bad value fails closed
  (VALIDATION) before the shell is used — test sends `';rm -rf /;'`, `tcp://`, `ssh://`, relative path: zero commands sent.
- **Command injection (scripts):** every new option is validated before anything changes (`--caddy-bind` IP characters only,
  ports 1-65535 numeric, distinct); values reach files and commands quoted. Test: `--caddy-bind '127.0.0.1; reboot'` rc 1.
- **Secrets:** none added. A dry run now prints file contents — only public material (public key in authorized_keys, sudoers rule,
  Caddyfile, daemon.json, quota helper); the existing no-secret test still holds. No secret in commands, logs or tests.
- **Least privilege:** sudoers unchanged (exactly reload caddy + quota helper). Rootless docker documented as the way out of the
  root-equivalent `docker` group; verify warns when a rootless user is still in `docker`.
- **Test seam:** `ONHOST_NODE_SYSROOT` is honoured only with `--dry-run`; a real run acts on `/` only (no env-steered root writes).
- **Availability of neighbours:** no Docker restart, no firewall default/enable on a shared host; Caddy never binds a taken port;
  `policy-rc.d` is removed again even when the install fails (only when the script created it).
- **Staging containment:** the Path A procedure keeps the deployer's checks (egress-blocked reject rules, expected-nonok, masked
  lanes); the freeze is lifted only for a documented window. No change to the deployer itself.
