## Objective

What outcome the user gets, in one or two sentences.

### Package backup-ops (points 1 and 18)

Operators see in `onhost:doctor` whether server and database backups sold to customers are actually taken (rule state,
missing `backup_storage`, stalled/paused schedules of every family, undeletable and orphaned volumes, backup tick
liveness and budget), a retried server backup no longer leaves a second full VM copy behind, and plans can be backed up
as often and as long as sold behind the owner's switch `backups.as_sold` with a read-only dry run first.

### Package mail-backups (point 3)

Mail plans' mailboxes keep the daily backups the plan sells (`backup_days`: Mail Business 14, Mail Enterprise 30) once the
owner switches the new default-off rule `mail.backup_retention` on: new mailboxes get the retention at creation, a paid
plan change applies it to the service's own mailboxes (a downgrade only by an operator's `--allow-prune`), and existing
mailboxes only through the dry-run-first operator command `onhost:mail:backup-retention`. Mailboxes the platform cannot
prove are its own are never written.

## Security considerations

backup-ops: no route, permission or customer parameter added. The backup marker is still derived from the row id only
(never from `desired`/context; a test sends `backup_marker: ''` and `backup_legacy: true` and they are ignored). Orphaned
volumes are only recorded, never deleted: the orchestrator's rule "never auto-delete a Proxmox volume that is not provably
ours". Both behaviour changes for existing services (`1h` → hourly, daily keepers = more storage) sit behind the
default-off rule `backups.as_sold`. Open (not this package): `automation.toggle` is NORMAL risk, so switching a
default-off rule on needs no step-up (risk-policy package).

mail-backups: no route or permission added; one new core action that customers cannot run (CustomerActionParams refuses
it before the bus reaches requestAction, for the API, stored hooks and Discord alike; the assistant does not offer it) and
that staff reach only at HIGH risk. Mailbox writes need a proven mail domain (`onh_` client, its group on the domain row,
the domain name) and a proven mailbox (same group, address inside the domain) — historical mail on the shared server is
never written, only reported (`not_ours`). The copy count is read from the service's entitlements, never from a request;
the adapter caps it at 1–365. A downgrade deletes backups at the panel's next run, so it is never automatic. No password
is ever sent back (the merge drops it). Everything that reaches existing services sits behind the default-off rule or the
dry-run-first command. Open: `automation.toggle` is NORMAL risk (risk-policy package), as for the other rules.

## Rollback

backup-ops: revert the commit. Operationally: switch `backups.as_sold` off — new hourly slots and new daily keepers stop; nothing is deleted en masse: keepers stamped while the rule was on (`meta.kept_as_sold`) live out their own `retention_until`, other rows beyond the generation cap are pruned at 50 per tick as before (review round 1). Doctor rows and the dry-run command are read-only.

mail-backups: revert the commit. Operationally: switch `mail.backup_retention` off — new mailboxes and plan changes stop
setting retention; what the panel already keeps stays (turning it back to the old default would itself delete backups, so
it is not done automatically).
