## Objective

Every service action asks for its own permission and risk: `ServiceActionCommand::permissionFor()` has no default arm (an unknown action fails closed),
deleting a backup or snapshot asks for its own permission with a fresh step-up, actions that hand out a shell or root ask for
`service.console`, and every destructive action (DestructivePreview) is HIGH with step-up. The secondary gates (spec apply,
action hooks, Discord) ask the same map (WP2).

## Security considerations

- The map has no default; unknown actions throw 422 before the authorizer decides (system actor included). Read paths (`ServiceFeatures::features`, `AssistantScope::mayRun`) only ever pass mapped actions or check first.
- Residual risk (not fixed here): `service.manage` (svc_manage, developer, power tokens) still reaches code execution as the site user through cron.create/update, file.save, node.create, file upload and deploy hooks, and inside a game container through gfile.save/gfile.upload (plugin jars, configs) and variable.set (egg startup variables); schedule.run fires an existing schedule, incl. a console schedule the owner created (the owner's fixed command, not arbitrary). The console line covers shells, not code execution.
- Residual risk (not fixed here): the console line is enforced from now on. Console access created before this fix through the old `service.manage` default (game sub-users from subuser.create, root password/SSH keys from access.reset, console-command schedules) stays on the panels while its holder keeps only svc_manage; RevokeDelegatedAccess acts only on future role/share events. Follow-up: an operator command, `--dry-run` by default.
- Residual risk (decision needed): subuser.create and a console-command schedule.create ask `service.console` but no fresh step-up, although both are persistent console grants.
- Residual risk (review round 2): `schedule.toggle` lets `service.manage` re-activate a console-command schedule the owner disabled (same class as `schedule.run`; making it payload-aware needs the stored schedule). A Pterodactyl scheduled backup task is understood to delete the oldest unlocked backup at the backup limit (NOT VERIFIED on the installed version): with a gbackup.lock unlock now `game.manage`, a `svc_manage` guest's backup schedule can rotate away only copies the owner left unlocked. An unmapped action throws inside `authorize()` before the bus's `denied` audit row (internal dispatch only).
- Staff widening at bus level: `backup_dr_admin` holds `backup.delete`, `infrastructure_admin`/`backup_dr_admin` hold `backup.policy.manage`. Over the customer API they are still refused because `/v1/services/{id}` first asks `service.read` (proved in ServiceActionRoleMatrixTest).
