## Objective

Every service action asks for its own permission and risk: `ServiceActionCommand::permissionFor()` has no default arm (an unknown action fails closed),
deleting a backup or snapshot asks for its own permission with a fresh step-up, actions that hand out a shell or root ask for
`service.console`, and every destructive action (DestructivePreview) is HIGH with step-up. The secondary gates (spec apply,
action hooks, Discord) ask the same map (WP2).

- The map has no default; unknown actions throw 422 before the authorizer decides (system actor included). Read paths (`ServiceFeatures::features`, `AssistantScope::mayRun`) only ever pass mapped actions or check first.
- Residual risk (not fixed here): `service.manage` (svc_manage, developer, power tokens) still reaches code execution as the site user through cron.create/update, file.save, node.create, file upload and deploy hooks. The console line covers shells, not code execution.
- Staff widening at bus level: `backup_dr_admin` holds `backup.delete`, `infrastructure_admin`/`backup_dr_admin` hold `backup.policy.manage`. Over the customer API they are still refused because `/v1/services/{id}` first asks `service.read` (proved in ServiceActionRoleMatrixTest).
