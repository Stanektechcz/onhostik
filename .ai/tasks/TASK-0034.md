## Objective

A tenant on an aaPanel node can no longer steer the panel's root file I/O into another customer's site or the node
itself: archives are judged before they are unpacked as root, the node shell no longer stages anything in /tmp, and on a
node several organizations share the operator can close the in-panel file manager and shell cron (dry run first).

## Context

Permission program key P0-03 (row IF-7, decision D11, exploit PA-02 CRITICAL / PA-03, owner default §10 O1).
`AaPanelTransport.php:235-246` checked paths lexically only while the file API runs as root; `AaPanelShell` wrote
`/tmp/<id>.out|.exit`, `AaPanelTransport::download` wrote `/tmp/onhost-dl-*.b64`, `restoreFromArchive` unpacked into
`/tmp/onhost-restore-*` — all world-readable by every site's PHP (`www`). D11: isolation is not engineered around the
TOCTOU race; multi-tenant nodes are closed instead.

## Decisions applied

- **D11 / O1:** closure only via `--apply` after the dry run and customer notice; per node; `--reopen --instance` reverts.
- **Security fixes apply directly** (parallel contract): archive preflight and the /tmp move need no switch.
- **Symlinks in archives (deviation, stated):** the program says "refused on symlink". A blanket refusal would refuse
  restores of legitimate sites (Laravel `public/storage` is an absolute link into the site; release switches are
  relative links) — a change of legitimate behaviour for existing customers, which the parallel contract forbids without
  a switch. So a symlink entry is refused when its target leaves the site, when any entry lies beneath it, or in a zip
  (zipinfo cannot show the target). Hardlinks, special files, absolute names and `..` are always refused.
- **"In-panel file editing" read as the whole file manager:** browse/read are closed too on a closed node, because the
  root read follows a planted link exactly like the write (the panel's own API key is a readable file); rename/copy/chmod/
  archive and site import (unpack into the site as root) close with it. Reversible per node with `--reopen`.
- **Shell cron:** no new code on a closed node (create, changed command, run on demand refused); re-writing the same
  command, pause/resume and delete stay — suspension depth and `cron-confine` keep working.
- **"Several customers"** = more than one organization among the platform's non-terminated services on the instance;
  historical sites the platform did not create are never read or counted (owner rule).
- The flag is read from the DB row on every guarded call, so long-running queue workers pick it up without a restart;
  an unreadable row counts as closed (review round 1).
- **Review round 2:** git deploy and staging close with the file manager on a closed node (per-node switch). Reading a
  file back (download) through the fd proof, the same-node staging chown without dereference and the deploy prune as the
  site user apply directly on every node: pure security fixes, nothing legitimate changes (a download of a link that
  leaves the site, or of a hardlinked file, is refused — the platform never packs such a file itself).
- **Review round 1:** PHP settings and one-click apps close with the file manager (root I/O into the site); on a closed
  node restores/migrations unpack as the site user (overlay, no delete) — both only behind the per-node `--apply`
  switch. Staging the archive and fixing the restore's tar/`src` bugs apply directly (security/bug fixes).

## Security considerations

Root file I/O on aaPanel is the boundary. Preflight is lexical on the archive's own entries (nothing on disk exists yet),
and since review round 1 it judges a root-only copy of the archive taken from the one file descriptor whose real path,
type and link count were proven. It does not cover a link already planted in the site that the panel's root unpack
writes through on an OPEN node; on a CLOSED node the transport refuses the panel's root file API inside the site at every
call, and uploads, unpacks, restores and deletes write into the site as the site's own shell user only (review round 2).
Every download (all nodes) reads a root-only copy of the one file it opened and proved (review round 2). Messages never
name the panel; refusal messages include at most 120 chars of an entry name of the tenant's own archive. The gate fails
closed. Still open by owner decision: terminal, Node projects, existing cron (code as the shared `www`). Still open on
OPEN nodes (D11, program §3): the panel's root write/upload/UnZip/Zip/delete inside the site (a race), `.user.ini` root
I/O, the staging relay's fixed-name root upload on a node that is not the source node.

None (no schema). Existing instances have no `tenancy` option → open, unchanged.

### Review round 1 (2026-09-27) — findings and resolutions

1. **security HIGH — archive in the site can be swapped / be a link to a neighbour's backup (TOCTOU, cross-tenant
   read). FIXED.** `AaPanelArchivePreflight::stage()` runs ONE root step: resolve the site root (`realpath -e`), resolve
   the target folder (`realpath -m`, must stay in the site), `exec 3< archive` once, require
   `readlink /proc/self/fd/3` inside the site root (catches a final link AND a folder link on the way — the reviewer's
   `cp -P` alone would follow folder links and copy a hardlinked file), `[ -f /proc/self/fd/3 ]`, link count 1, then
   `cat <&3` into `/www/.onhost-stage/stage-<id>` and list THAT copy. UnZip gets the copy as `sfile`; the copy is removed
   in `finally`, and on any refusal. Echoed entry names now come only from the tenant's own archive. STAGE_DIR is under
   /www (root-owned, beside the sites), not /root: a site-sized copy must not fill the root file system.
2. **security HIGH — a closed node does not close PA-02 (root unpack/restore into the live site). FIXED.** On a closed
   node `extract` (restore, archive restore, migration target) and `restoreFromArchive` unpack as root only into a fresh
   0700 folder in STAGE_DIR (entries already judged, nothing there is the tenant's), then `tar -cf - | su -s /bin/bash
   www -c 'tar -xf - …'`: every write inside the site happens as `www`, a planted link gives nothing the tenant does not
   already have. No UnZip, no root rsync/cp, no root `chown -R`. Restore there is an overlay (no `--delete`); the root
   `.user.ini` is never written. Notice text and command output corrected.
3. **security MEDIUM — php.settings / app.install are root writes into the site. FIXED (closure).** `php_settings` and
   `apps` flags off on a closed node; `phpSettings`, `setPhpSettings`, `installApp` refuse. Open-node `.user.ini` →
   follow-up finding above.
4. **security MEDIUM — terminal / Node projects / existing cron as `www`. RECORDED as owner decision** (not code): see
   Findings; the command warns on every run; notice wording corrected (handoff).
5. **security MEDIUM — `instance.upsert` replaced the whole options object, reopening a node silently. FIXED.**
   `ProviderInstanceService` keeps an existing `tenancy` unless the input names it; audit detail `options_changed` +
   `tenancy {from,to}`.
6. **security MEDIUM — one org + historical sites never closable. FIXED.** `--apply --instance=<key> --force` (refused
   without `--apply` or without `--instance`); recorded as `tenancy.forced`.
7. **reviewer HIGH — gate fell back to the adapter's in-memory copy on a DB error (fail-open). FIXED.** `state()` → null on
   error; `assertOpen` throws TRANSIENT (retryable, nothing written), `closed()` answers true (features off, closed-node

8. **reviewer MEDIUM — zip symlink refusal is an unswitched behaviour change. ACCEPTED, recorded.** A knowingly
   unswitched change, not an oversight: zipinfo cannot show a link's target, so an in-site zip link cannot be told from

9. **qa MEDIUM — no negative test for `restoreFromArchive`. ADDED** (the 11 "escaping archives" against the restore: no

### Review round 2 (2026-09-27) — findings and resolutions

1. **security HIGH — `download()` read the file by name as root (`stat`, `tail -c`); FinalArchive and the staging relay
   pack into the site and read back, so a swapped-in link returned /root/.my.cnf, the panel's keys or a neighbour's
   wp-config.php as the tenant's backup. FIXED (every node).** One root step opens the file once (`exec 3<`), requires
   `readlink /proc/self/fd/3` inside the transport root (`realpath -e`; a panel-folder transport with root `''` has no
   boundary), `[ -f ]`, one name — or, with two names, a file owned by the sites' own users (`www`, `oh*ag`), which the
   tenant can read anyway; then `head -c 2GB+1 <&3` into `/www/.onhost-stage/get-*` and every chunk comes from that copy,
   removed in `finally`. On a closed node the final archive no longer packs into the site at all: `archive()` refuses there
   and FinalArchive falls back to its second path, the panel's own backup (root-only folder). Not done: repacking the
   FinalArchive/staging archives straight into a root-only folder (the "better still") — both files are outside this
   task's paths and the fd proof already closes the read; follow-up for their owner.
2. **security HIGH — same-node staging: root `rsync -a` then `find … -exec chown` (dereferences) → a planted
   `x -> /etc/shadow` became the site user's: root on the node. FIXED (every node) + staging off on closed nodes.**
   `find … -execdir chown -h`: `-h` changes the link itself, `-execdir` runs from inside the folder find already holds, so
   no folder on the way can be swapped for a link in between (chown -h alone still follows the folders of the path).
   Running the sync "as www" was not possible: `www` cannot run a binary on a hardened node, and neither site's shell
   user can both read production and write staging. The root rsync writing into staging remains the D11 race on open
   nodes (closed nodes: staging off). D16 forensic look-back → handoff (TASK-0038 / orchestrator; never run live here).
3. **security HIGH — deploy stays on closed nodes and writes as root inside the site (deploy key via
   CreateDir/SaveFileBody/SetFileAccess; prune `xargs rm -rf` as root follows a `releases` link). FIXED.** `deploy` off on a
   closed node; the transport itself refuses `mkdir`/`write`/`chmod` there, so the prepare step of a deploy or rollback
   fails with the reason (also for one queued before `--apply`); the prune runs as the site user on every node
   (DeployWorkflow; the releases are that user's own clones). Handoff, KEEPS/LOSES text and notice corrected.
4. **security MEDIUM — the transport had no gate; work queued before `--apply` still did root I/O. FIXED.** The site
   transport asks the gate at every call (`Closure(): ?bool`): `list`, `read`, `write`, `mkdir`, `rename`, `copy`, `chmod`,
   `archive` refuse (VALIDATION; TRANSIENT when the row is unreadable); `upload`/`delete` go through the site user; the
   dry run also prints "let queued web operations finish or cancel them before --apply" (runbook step in the handoff).
5. **qa HIGH — `upsert()` lost update (snapshot before the transaction, no lock). FIXED.** The row is re-read with
   `lockForUpdate()` inside the transaction; `options`, `options_changed` and the audit's `tenancy.from` come from it.
   Test simulates the race: the concurrent closure commits right after the pre-transaction read (DB::listen).
6. **qa MEDIUM — command check-then-act. FIXED.** `write()` re-checks and dispatches inside one transaction holding the
   row lock; a second run writes nothing and prints `already closed (by another run meanwhile)` (one audit row). A bus
   refusal is caught inside and re-thrown after commit, so the bus's `failed` audit row is not rolled back.
7. **qa MEDIUM — drift between dry run and `--apply` untested. ADDED** (coverage only; passed first run: the services
   are re-read at `--apply`, terminated ones do not count → "Nothing to close").
8. **Found on the way, HIGH (my round-1 code): the closed-node site-user unpack/restore ran `tar` as `www`, which the
