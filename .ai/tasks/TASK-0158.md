## Context

`PROMPT-faze-K-2026-10-11.md` package K5 (was J5). Open question of the prompt: 000950 stops on a genuine double *before* the new code
is live, so finance could only cancel on the old release (no such code), in a half-migrated database (deployer rc 4: new code checked

Design that satisfies both: the four-eyes command can only run on released code, so the new migration `000949` (sorts before 000950,
runs first on a database that has not run 000950) applies I-R6 *only as far as a migration may* — it **sets the newer row aside**
(invoice link moved to `duplicate_invoice_id`, `duplicate_of_id` = the standing row, unpaid `payable` → `duplicate`, never payable;
amounts untouched) so 000950 builds its index; the correction itself (`cancelled` + reversal, or a payable minus for a row already
paid out) is finance's bus command after the release. A newer row in an open payout (`allocated`) cannot be held safely (a rejected
payout would make it payable again): `000949` stops before any change and names the payout (finance finishes/rejects it on the
running release, deploy again). Remainder groups stay 000950's (same test, copied).

Note: the prompt named the command `partners.commission.cancel_duplicate`; the existing `PartnerCommand` convention gives
`partner.commission.cancel_duplicate` (op `commission.cancel_duplicate`).

## Security considerations (self-check, `ecc:security-reviewer` style)

- **Authorization:** staff route; `partner.manage` (BillingFinanceAdmin, platform_owner); `PartnerCommand::riskLevel()` HIGH +
  `requiresStepUp` + `requiresApproval` for `commission.cancel_duplicate` (catalogue floor of `partner.manage` is HIGH anyway). The
  approval is bound to the command name, the payload hash (commission id + reason) and the requester; self-approval is refused
  (tested); `ONHOST_FOUR_EYES=false` → the sole approver's time lock (existing authorizer). Tokens: staff permission without a token
  scope → refused by the authorizer (TokenScopes deny by default).
- **Money:** append-only — a new reversal row, never an amount edit; integer minor units; a paid row is never "un-paid" (minus on the
  next payouts instead, the existing post-window semantics). `duplicate` is not `payable`: every payout path selects `state = payable`
  (`PartnerPayouts::allocate`), the maturing job selects `pending`, a payout rejection resets only rows with its `payout_id` (a
  set-aside unpaid row has none; allocated ones are refused by the migration).
- **Idempotency / races:** row `lockForUpdate`; existing-reversal check; partial unique index on `cancels_id` as the race guard
  (savepoint, `UniqueConstraintViolationException` → 409); `onceKey` idempotency on the route.
- **Input:** path id used only through `whereKey`; reason validated 10–500 and checked again in the handler.
- **Migration (§5):** no column or data removal; the set-aside moves the invoice link into a new column (reversible, `down()` tested);
  stops before any change on the unsafe case; one row per paid invoice of an attributed client (small); old code on the new schema
  keeps working (nullable columns; `duplicate` is not payable for it either). 000950's own `down()` turns `cancelled` into `payable`
  — a cancelled duplicate and its cancelled reversal net to zero, as the 000950 comment says for credit-note cancellations.
- **Events / secrets:** payload `invoice` (number), `amount`, `outcome` — no internal ids beyond the aggregate, no redaction fragment.
- **Tenant:** global staff action; the partner portal shows nothing new; the notification goes to the partner's organization only.
- Findings: none MEDIUM or higher. LOW (accepted, documented): a group that mixes a payout remainder and a genuine double is set aside
  as a whole (000950 treats groups wholesale too); finance compares amounts before cancelling.
