# TASK-0013: A hosting that ends stops pointing its DNS at the node

- **Status:** INTEGRATED
- **Priority:** P1
- **Risk:** HIGH
- **Owner:** onhost-provisioning
- **Reviewers:** onhost-reviewer + onhost-qa + onhost-security

## Objective

When a web hosting is removed, the DNS the platform published for it stops pointing at the node — the site's
records and the mail records of its mail domains — while everything the customer wrote themselves stays.

## Context

Audit row 100. Three publishers write a hosting into DNS (`web:<service>`, `service:<service>`, `mail:<domain>`)
and the purge removed none of them. `platformDnsStep` cleaned only the platform's own zone
(`<label>.web.onhost.cz`), and swallowed its own failures with a comment claiming the reconciler would retry —
it does not: `DnsService::commit()` publishes to the provider first and leaves the database untouched on a
failure, so the platform and the provider still hold the same record and the nightly drift check sees no
difference.

## Out of scope

- Existing services: nothing sweeps zones for records of services that ended before this change.
- Parking. The domain is left pointing nowhere; putting it on the parking address is an action of its own
  (`domains.use_onhost_dns`, template `parking`) and a product decision, not a side effect of a deletion.
- Retrying a failed DNS commit later. `DnsChange` rows in state `failed` are still nobody's work — see Concerns.

## Contracts affected

`service.purge.leftover` gains the kind `dns` (entries read `zone (owner)`); the step's context keys
`dns_zones`, `dns_removed`, `dns_left` replace `dns_zone`/`error`. No endpoints, schema or config keys.

## Acceptance criteria

- [x] After a purge, the site's A/AAAA and the mail records of the service's mail domains are gone from the
      customer's zone.
- [x] A record the customer made themselves (`managed_by = customer`) survives.
- [x] A zone that refuses the change does not fail the termination and is named to the operators.
- [x] The hosting hostname in a platform zone is still removed (the old behaviour, kept).

## Required tests

`tests/Feature/Dns/ServiceDnsCleanupTest.php` — failing-first: after the purge the zone still held `@ A`,
`www A`, `@ MX` and the SPF `TXT`, and nothing was reported.

## Security considerations

A domain resolving to a shared node that no longer hosts it shows the visitor whatever that node answers for an
unknown name — in practice another customer's site. Mail is worse: MX, SPF and DKIM kept authorising a node the
customer no longer uses. Only records whose publisher is this service are removed, so nothing of a neighbour or
of the customer's own making is in reach.

## Migration considerations

None: no schema change, no backfill, no sweep.

## Rollback

Revert the merge commit; the step returns to cleaning the platform zone alone.
