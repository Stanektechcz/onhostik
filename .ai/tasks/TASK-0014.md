## Objective

The platform never writes to, suspends, changes or deletes a site on ISPConfig or aaPanel that it did not create
itself. Historical sites (made by hand before ONhost) stay untouched; resources the platform created stay fully
manageable.

## Context

The owner's rule (2026-09-24): „Do již existujících webů na ISPconfig a AAPanel nesmíme nijak zasahovat při vývoji.
Toto jsou historické weby do kterých nový systém nesmí jakkoliv zasahovat. Na panelech mimo historické weby však může
provádět úpravy, vytvářet nové weby a ty editovat a spravovat."

Read in the code first: `IspConfigWebProvider::provision()` and `AaPanelWebProvider::provision()` looked the name up on
the node and returned `alreadyExisted: true` for whatever site was there; `IspConfigWebProvider::createMailDomain()`
did the same for mail domains and `createDatabase()` for databases of any site. Every `StepContext::bind()` caller
writes `ownership: ['managed_by' => 'onhost']` unconditionally, and nothing reads `ownership`. So an order for a name
that already lived on a node tied the service to a historical site, which the platform could then suspend, resize and
finally delete (the deletion guards compare the domain and the site's own system user — both matched).

## Out of scope

- An explicit adoption flow for a historical site (brain H304: read-only inventory, then an explicit confirmation of
  ownership and of which fields ONhost will manage). Until it exists, a historical site simply cannot be taken over.
- Catching the name at the cart. The node is chosen at provisioning, so the refusal comes after payment and the
  order fails (the order-failure path refunds). Checking the executor's nodes at quote time is a follow-up.
- Existing bindings: nothing is swept (the standing rule). The platform is not live; bindings made on staging were
  made by the platform's own test orders.

## Contracts affected

`provision()`, `createMailDomain()` (ISPConfig) and `createDatabase()` (ISPConfig) throw `ProviderException(CONFLICT)`
for a pre-existing resource that is not provably ONhost's. `provider_bindings.ownership` gains `provenance`
(`created` | `recovered`) for web sites. No endpoints, events, schema or config keys.

## Acceptance criteria

- [x] A historical ISPConfig site (another client) is refused before any write — no site, no client, no limits.
- [x] The platform's own ISPConfig site found again on a retry is still recovered.
- [x] A historical ISPConfig mail domain (another client group) is refused before any write.
- [x] A historical aaPanel site (no `onhost:<service>` remark) is refused; the service's own site is recovered; a site
      of another ONhost service is refused too.
- [x] A provisioning that meets a historical site fails with no binding written.
- [x] A same-named database of another ISPConfig site is refused.
- [x] A mail domain carries its name; no mailbox, alias, forward, fetchmail or spam query is ever sent with `%@` alone.
- [x] A web hosting without a mail domain lists no mailboxes, and a panel without mail still answers `feature_unavailable`.

## Required tests

`tests/Feature/Provisioning/ResourceProvenanceTest.php` — failing-first: four of five cases failed on the old code
(the saga case with "a binding exists"), the retry case passed as it should.

## Security considerations

This is the owner's hard rule and the most destructive path the platform had: adopting a stranger's site made every
later write — suspension, limits, deletion with databases — land on it. Proof of ownership is taken only from the
panel itself; anything unproven is refused, and a panel that will not say whom a mail domain belongs to is treated as
"not ours" (a retryable error is still retried, never turned into a final refusal).

None — no schema change, no backfill, no sweep.
