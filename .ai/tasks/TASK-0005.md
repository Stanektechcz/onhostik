## Objective

A customer acting on their own web hosting or mail service can no longer reach another customer's shell user,
database user or mailbox on the same ISPConfig instance.

## Context

Found by a six-lens audit of the web hosting path and then verified by reading the code directly. ISPConfig's remote
API is reached through **one administrator session per instance** and never asks whose record a `primary_id` names —
the adapter's own comments say so ("a mail domain's id among web sites is a stranger's site"). The platform validates
a customer's `remote_id` for its **shape only** (`ServiceService`: `/^[A-Za-z0-9:_.-]{1,120}$/`). On a shared node
the ids are consecutive integers.

Nine of the eleven id-taking methods in `IspConfigWebProvider` resolved the id against the site's own listing first.
Three did not, and the mail path built its `ResourceRef` straight from the parameter. Audit row 92,
`docs/runbooks/security-boundaries.md` §19.

## Contracts affected

None. No endpoint, event, schema, config key or provider call changes shape. Three adapter methods and three saga
arms now read one listing before they write, and refuse an id the service does not own
(`ProviderException(NOT_FOUND)` in the adapter, `StepResult::fail(..., retryable: false)` in the saga).

## Acceptance criteria

- [x] A stranger's shell-user id, database-user id or mailbox id never reaches the panel.
- [x] The same actions still work for the ids the service really owns.
- [x] The existing "database user still owns databases" conflict is unchanged.
- [x] A listing that fails is a provider error (retried), never read as "not yours".

## Security considerations

This *is* the security fix. It closes cross-tenant compromise on a shared ISPConfig node: reading a neighbour's site
files over SSH (and their database through `wp-config.php`), taking over their MySQL user, deleting their database
user, and taking over or deleting any mailbox on the mail server.

**Not fixed here, and worth an operator's look before production:** the platform cannot tell whether any of this has
already happened on the live instance. `provider_calls` of the last 90 days hold the `sites_shell_user_update`,
`sites_database_user_update`, `sites_database_user_delete`, `mail_user_update` and `mail_user_delete` calls that were
made — an operator can compare each `primary_id` against the service that asked.
