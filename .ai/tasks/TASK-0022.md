## Objective

### Package risk-policy (owner decision 13)

Every change of a price or a plan in the admin configuration takes a step-up **and a second person**; HIGH means a step-up
only; withdrawals (discount/promo code deleted, code paused, product off sale) stay with one person and a step-up; an
unclassified catalogue operation is four-eyes (fail closed); switching an automation rule takes a step-up.

### Package catalog-versions (owner decisions 2, 4, 5, 6, 11, 18, 21)

Plans stop promising what the platform does not provide, as NEW plan versions (existing versions, services and subscriptions
untouched): a code-defined revision `2026-09-honest-promises` (`domains/Catalog/CatalogRevisions.php`) published by the
operator command `onhost:catalog:revise` (dry run by default, `--apply`) through `CatalogCommand plan.publish`. The e-shop
product count is fair use, `cron_concurrency` is named in words, a new managed database never claims PITR, the seeder can
no longer rewrite a sold version, and the public student/school page is withdrawn.

- NOTE (risk-policy, owner to confirm) — the boundary of "price/plan change" is CatalogCommand only. Not four-eyes: LoyaltyCommand levels/campaigns/streak (HIGH), ProvisioningCommand `registrar.costs.upsert`/`registrar.policy.set` (NORMAL under HIGH provider.instance.manage), chargeback settings, partner tiers/commissions. Each can opt in with `requiresApproval()`.
- NOTE (risk-policy) — `onhost:catalog:state active` on the server runs as the system actor and puts a product on sale without a second person (server access = operator). Documented as the emergency-brake path for `draft`; `active` via CLI is not gated.
- NOTE (risk-policy) — ASSUMED, not traced: deleting a ProductOption (`option.delete`) does not break renewals of services that bought it; classed four-eyes as a precaution.
- NOTE (risk-policy) — header-less catalogue writes now carry the minute in their idempotency key (`onceKey`); API clients that retry a price change after more than a minute without an Idempotency-Key re-execute it (upserts are idempotent; a plan publish would need a new approval because its `base_version` moved).
- NOTE (catalog-versions) — `onhost:catalog:revise --apply` publishes as the system actor: `IdentityCommandAuthorizer` allows system commands without step-up or a second person, so decision 13's four eyes do not apply on the CLI (same as `onhost:catalog:state active`). Gate = shell access + code review of `CatalogRevisions`; a revision cannot pass prices or features. Owner to confirm.
- NOTE (catalog-versions) — ASSUMED, not verified against production: the current versions there still carry these keys/values. The command is stateless and skips what is gone; the dry run shows it.
- NOTE (catalog-versions) — decision 21: only the `sol-edu` page is withdrawn. Two other prototype mentions stay: the about page row "Školy a studenti — zdarma" (`Onhost.dc.html` osItems) and the eco list "Free tier pro open-source projekty a studenty"; footer/nav links to `sol-edu` now lead to the notice page. Follow-up: SurfaceRenderer seams for those two if the owner wants them gone.
- NOTE (catalog-versions) — the static database page kpis ("1 s granularita PITR", failover/HA) and the Vector DB page still say PITR (prototype copy, `onhost-svc-web.js`/`onhost-svc-compute.js`); only chips were replaced. Needs owner copy.
- NOTE (catalog-versions) — a promo price on a plan's current version is not carried into the new version (PlanVersioning); the dry run warns per plan.
- NOTE (catalog-versions, for limit-raise) — `CatalogRevisions` changes existing plans and product descriptions only; creating a new product/plan (the limit-raise product) needs a new catalogue op (price-changing → four-eyes via the console, system actor on the CLI) and a revision shape for it.
