## Objective

Phase C, packages C1 + C4 (frontend integration layer): the browser modules in `apps/surfaces/api` call only routes the
server has, with the headers they mean to send, and one user intent travels under one Idempotency-Key. A failed read is
shown as an error, never as an empty list, and list loaders read every page.

## Context

`brain.ps1 task start` halted on Composer stderr under PowerShell 5.1 after creating the worktree (known bug); the worktree
was finished by hand (`composer install`, `task claim`), and this file was written afterwards.

C1 findings: the chat's restart chip used the `/power` shorthand with a body the action route reads only as a fallback;
`OnhostApi.get(p)` took no headers, so the staff game console's log read dropped `X-Organization`; the staff drawer spread
the string from `key()` into a header map (`Object.assign({}, 'ui-…')`), so no Idempotency-Key was sent with an assistant
action. C4: `key()` was new on every click (a double click or a retry was a second request to the server), PUT / PATCH /
DELETE sent no key, the staff bank line id carried `Date.now()`, the store / staff console / domains turned failed reads
into `[]`, and lists were cut at `limit=100/200/500` (the API caps a page at 200).

## Security considerations

Keys are kept in memory only. A request with the same key and another body is refused by the middleware (409), so the key
is tied to a fingerprint of the body. The server's invoice-pay command key does not include the invoice id (see Findings).

## Findings

- HIGH routes/api.php — `POST /v1/domains/{domain}/holder` is not registered although `DomainController::holder` exists and
  the panel's holder-contact screen calls it (404). Allow-listed in the contract test with the reason; owner of
  routes/api.php to add the line, then remove the entry (the test fails once the route exists).
- LOW app/Http/Controllers/Api/V1/InvoiceController.php:68 — the bus key `invoice.pay:<op>:<header>` does not name the
  invoice: the same header for two invoices of one organization returns the first answer. The frontend now scopes its key per
  document, so it never sends one key for two invoices.
