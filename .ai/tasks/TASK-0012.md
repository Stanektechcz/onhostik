# TASK-0012: The primary binding of a service must not be a coin flip

- **Status:** SELF_VERIFIED
- **Priority:** P0 (the nightly PostgreSQL run of the whole suite fails on it)
- **Risk:** HIGH
- **Owner:** onhost-provisioning
- **Reviewers:** onhost-reviewer + onhost-qa + onhost-security (the proof before a deletion depends on it)
- **Branch:** `fix/TASK-0012-the-primary-binding-of-a-service-must-no`

## Objective

`Service::primaryBinding()` answers with the resource the service actually **is**, whatever order the rows come
back in.

## Context

`pest-postgres` failed on `development` twice (2026-09-24 15:31 and 16:25) and again on the TASK-0011 branch, each
time in `FinalArchive` → `ServiceIdentityCheck` with `binding_type` mismatched and **9 of the 5 required points
matched**. A web hosting binds its site *and* the mail domain it was given for mailboxes; both rows are written by
the same operation within the same second, and `primaryBinding()` ordered by `created_at` alone. SQLite answers
with the row written first, PostgreSQL with either — so the platform sometimes decided a web service *was* its mail
domain. It is not a test flake: the same tie exists in production, and 24 call sites ask this question.

## Out of scope

- Existing services: nothing is written or migrated. The change is a read path only.
- The `created_at` precision of `provider_bindings` (seconds). Ordering must not depend on it at all, which is
  exactly what this change achieves.

## Contracts affected

`ServiceIdentityCheck::TYPES` becomes public (it is now the one answer to both "may this family bind this type?"
and "which of my bindings am I?"). No endpoints, events, schema or config keys.

## Acceptance criteria

- [x] A web service that also binds a mail domain answers with its `web_domain` binding — even when the mail row is
      older.
- [x] `ServiceIdentityCheck` recognises such a service again (`binding_type` passes).
- [x] The selection is deterministic on any database: own family first, then `created_at`, then the id.

## Required tests

`tests/Feature/Services/PrimaryBindingTest.php` — failing-first: the mail binding written a second earlier won.

## Security considerations

This is the identity of a resource before a deletion. `ServiceIdentityCheck` exists because a mail domain's number
matched a stranger's web site, and a coin-flip primary binding is the same shape: everything else (`assertWebDomain`,
`ownRow`, the domain and `system_user` guards) is what kept it from becoming an incident. Making the answer
deterministic removes the coin flip itself.
