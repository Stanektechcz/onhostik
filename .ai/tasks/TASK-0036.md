## Objective

Nobody can hand out, change or take away more access than they hold themselves: the owner cannot be demoted by a mail
link, a stranger cannot be pulled into an organization by id, a member is changed or removed only by somebody who covers
their role, project roles pass the same check with a fresh step-up, and an idempotency key answers only for the
organization, service, action and person that sent it.

## Security considerations

- GrantPolicy compares with `Authorizer::permissionsAt()` (what the actor effectively holds now, expiry included) and the
  union of the catalogue line and the DB rows for the role granted (an IAM-edited role cannot be under-counted).
- System actor: target invariants apply, no grantor comparison. Staff: not compared (unchanged; IF-8/P0-08). Service
  accounts and AI: compared as principals (fail closed on unknown actor).
- `attachMember` refuses `owner` for anybody but `owner_user_id` and anything but `owner` for them (I4) — any caller.
- `acceptInvitation` keeps a current membership unless the link strictly widens it with no earlier end (I9).
- IF-12 namespace = organization | service | action | actorType:actor (on-behalf user first); request hash = action + canonical params.

## Migration considerations

None (no schema change). Operations started before deploy keep their raw keys; a client retrying across the deploy with the
same key gets a new operation id — the per-service "one operation at a time" guard (409 `operation_in_progress`) prevents a
duplicate run while the old one is still active.

## Rollback

Revert the commits; nothing persistent depends on them except operation keys written in the new format (harmless to old code:
it looks up by exact key, so a retry after rollback starts a fresh operation, again guarded by `operation_in_progress`).

- D1 (one GrantPolicy), program §3 I1, I2, I3, I4, I8, I9, I11; §10 defaults (no owner question touches this slice).
- Pure security fixes of illegitimate access applied directly (no switch): non-member targets, owner demotion, invite of a
  current member, cover check on change/remove, project-role allow-list, idempotency scoping.

### Review round 1 (2026-09-27) — findings and resolutions

Scope extended for R1-1 (recorded here, no other Phase-0 task owns these files): `app/Http/Controllers/Api/V1/ServiceController.php`
(`action()` key + private `actionKeyPrefix()`), `domains/Services/Commands/ServiceActionCommand.php` (`idempotencyKey()` override).
`platform/Commands/IdempotencyStore.php` and `CommandBus.php` deliberately NOT touched (see R1-1).

- **R1-1 HIGH (security) — bus replay crossed members and services of one organization. CONFIRMED, fixed.** The bus keeps its answer
  under (`service.<action>:<header>`, organization) and answers before the handler, so member B's header for service Y got member A's
  operation on service X (nothing ran on Y). Fix: the controller key is `service.<action>:<service id>:<16-hex actor digest>:<header>`
  (actor = on-behalf user first, as the operation namespace); `ServiceActionCommand::idempotencyKey()` (what the bus uses) appends a
  keyed fingerprint of the payload, while the handler still passes the plain `$command->idempotencyKey` to `requestAction` — so a
  different body passes the bus and `ServiceService` answers 409 `idempotency_key_reused`, also when the HTTP layer kept no answer.
  `uploadFile()` (:154) needed nothing: its key embeds a fresh random `game-uploads/tmp/<24>` path, so two requests never share a bus
  key (and the payload fingerprint now applies there too). Why not `IdempotencyStore::scope()` per actor: it changes replay for every
  command of the platform (spec, policy, chargeback, wallet…), beyond IF-12 and this task's slice; the remaining same-org cross-actor
  replay of OTHER commands is G12's rest → follow-up (handoff). G12 is closed for service actions only.
- **R1-2 MEDIUM (security) — `request_hash` was an unsalted sha256 over params carrying passwords. CONFIRMED, fixed:** HMAC-SHA256
  keyed with `app.key`. The bus fingerprint (R1-1) is keyed the same way. Consequence: after an `app.key` rotation a retry of an older
  request with the same key gets 409 instead of its operation (documented; rotations are rare and keys are per request).
- **R1-3 MEDIUM (security) — `DomainService` still looks operations up by the caller's raw key (SE-5 for domains). CONFIRMED, not in
  this slice:** `domains/Domains/DomainService.php` is outside the owned paths and IF-12 names `requestAction` only. SE-5 is NOT closed
  in the audit; follow-up recorded in the handoff (shared scoping helper for DomainService).
- **R1-4 MEDIUM (qa) — read-then-act races.** `requestAction`: CONFIRMED that the loser got a 500 (UniqueConstraintViolationException);
  the unique index on `operations.idempotency_key` (migration 000300) already made the winner single. Fixed: the violation is answered
  409 `operation_in_progress` (the bus transaction rolls the loser back). `invite` / `already_member`: DISPUTED as a defect — the 409 is a
  courtesy, not the protection. Two concurrent invitations for a NON-member only produce two pending links, which sequential invitations
  may do too (only a current membership blocks, by design); for a current member the protection is at acceptance (I9 `widens` inside the
  accept transaction + I4 in `attachMember`), proven by the first GrantPolicyTest case ("a link mailed before … still cannot lower the
  owner"). A unique index on pending invitations would be a schema change that also forbids a legitimate re-send → not done.
- **R1-5 MEDIUM (qa) — missing cases. Added** (green at first run — coverage, not defects): re-invite after removal (201); lapsed
  member: removable, `change_role` → 404 (the recorded decision "renewing ended access = a new invitation"; the reviewer's "role change
  should also succeed" contradicts it and was not adopted), re-invite of a lapsed member allowed; expired and already-used invitation
  tokens → 410; soft- and hard-deleted user ids → 404 with nothing written. NOTE (pre-existing, not changed): a hard-deleted user's
  membership row stays (no FK cascade) and cannot be removed through `remove_member` (404) — belongs to the erasure flow.
- **R1-6 NEW, pre-existing, not fixed (outside scope):** without an `Idempotency-Key` header `ApiController::idempotencyKey()` builds the
  key as unsalted `sha256(user|path|json(body))`; for a service action that key is stored permanently in `operations.idempotency_key`,
  and the body may carry a password (mailbox/FTP/db) — the same offline-verifier class as R1-2. One-line HMAC fix in a shared file used
  by every controller → follow-up in the handoff.
