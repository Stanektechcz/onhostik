## Objective

Close the loophole in `PlanPromises` that let the price-list/presentation code count as "the platform applies this
number" (brain card H278: a plan must never promise a limit the backend does not enforce). Introduce a hand-verified
`MetricRegistry` of what actually measures or enforces each catalog number today, use it for the numeric-promise
guard, and turn every currently-broken promise into one documented, ratcheted `KNOWN_GAPS` entry instead of a false
pass. Behaviour is unchanged: no prices, seeders, adapters or services were touched, only the guard's honesty.

## Context

`domains/Catalog/PlanPromises::readInSource()` excluded only paths containing `/Catalog/` from its "is this key read
by real code" text scan. `app/Http/Support/CatalogPresentation.php` — the price-list wording — sits outside that
exclusion and names every entitlement key it displays, so it satisfied its own guard. Read-only analysis (this task)
confirmed the guard was passing keys nothing measures or enforces: `products` (e-shop), `connections` (managed DB),
`dedicated_outbound_ip`/`dedicated_db` (mail/managed), and more found in the course of the fix (see Findings).

  real gap as an operational fact. They were added to `KNOWN_GAPS` instead, alongside the numeric gaps (the ratchet
  mechanism applies uniformly regardless of PHP type in this implementation).
  **DECIDED (orchestrator, this pass):** `dedicated_outbound_ip` and `dedicated_db` stay in `KNOWN_GAPS` — honest,
  not `FAIR_USE` (they are unbuilt, not an operational fact like a CA's warranty or a CDN's PoP count). Owner may
  still overrule.

### Independent review pass (reviewer, QA, security) — resolutions

1. **HIGH (QA)** — nothing asserted every `PlanPromises::KNOWN_GAPS` key had a `MetricRegistry` row with
   `status === GAP` and a non-empty `reason`; a key could be added to the ratchet without a matching registry entry,
   or a registry row could drift out of GAP status while the ratchet still listed it. **Resolution:** added
   `it('names a GAP row in MetricRegistry, with a reason, for every KNOWN_GAPS key')` to
   `tests/Feature/Catalog/PlanPromisesTest.php`. Confirmed failing-first by deleting the `aliases` row from
   `MetricRegistry::REGISTRY` and re-running (`"KNOWN_GAPS key 'aliases' has no MetricRegistry row at all"`),
   restored, green again.
2. **HIGH (QA)** — no test covered the two new `onhost:doctor` rows (`catalog: no known metering gap` /
   `catalog: the metering gap ratchet is not growing`). **Resolution:** added two tests to
   `tests/Feature/Platform/DoctorCommandTest.php`: known gaps stay WARN in both non-production and production
   (forced via `app()->instance('env', 'production')`, since the ratchet-presence row is not `blocking`), and a new,
   untracked numeric entitlement injected onto a real plan version is WARN outside production and FAIL, naming the
   key, once forced into production.
3. **MEDIUM (reviewer)** — `MetricRegistry::isKept($key)` ignored the row's `families` field, so a key verified only
   for one family (e.g. `mail`) passed for any plan selling the same key name. **Resolution:**
   `MetricRegistry::isKept()` now takes an optional `$family` and fails the check when the family sold is absent
   from the row's own `families` list, before ever looking at `status`. `PlanPromises::rawUnkept()` derives the
   family from the version's own plan/product (`Plan::query()->find($version->plan_id)?->product?->family` — written
   this way, not the shorter `$version->plan?->product?->family`, because Larastan could not carry the `Plan` type
   through the nullsafe relation chain and flagged `Model::$product` as undefined; the explicit query resolves to a
   concrete `Plan` and passes PHPStan level 5 clean). Test:
   `it('reports a registry key sold on a product family its row never verified')` (`quota_gb_per_mailbox`, verified
   only for `mail`, sold on a web-hosting plan). **Family-scoping the whole catalogue surfaced four consequences,
   verified against the real adapter/workflow code, not assumed:**
   - `nvme_gb` — families list was missing `data`; `ServiceService` dispatches `ProvisionVpsWorkflow` by
     `executor === 'proxmox'`, not by family, so the managed-database product (family `data`, executor `proxmox`)
     sizes its disk from `nvme_gb` exactly like a VPS/VDS. **Incomplete list, extended** (not a gap).
   - `mailboxes` — families list was missing `addon`; `Addons::patch()`'s `mail-hosting` case adds the add-on's
     `mailboxes` onto the parent service's own `mailboxes` entitlement, which is then enforced the same as any other
     `mailboxes` sale. **Incomplete list, extended** (not a gap).
   - **`backup_days` — new honest gap found by family scoping.** Sold on `db-s`/`db-m` (managed database, family
     `data`); `BackupScheduler::tick()` queries `Service::whereIn('family', ['web','managed','mail'])` only — a
     managed database's backup retention promise is enforced nowhere. Kept for web/managed/mail. Added to
     `KNOWN_GAPS` and to `MetricRegistry::REGISTRY['backup_days']` (status flipped to `GAP`, `families` extended to
     document all four sold families, `reason` explains the partial enforcement — same pattern already used for
     `php_workers`).
   - **`vcpu` — new honest gap found by family scoping.** Sold in every game plan's entitlements; grepped
     `providers/Pterodactyl/*.php` and the game provisioning workflows for `vcpu` — no match. `PterodactylGameProvider`
     only reads `cpu_pct` and `pids` (the `limits` bag) to size a container; `vcpu` is never sent to the panel. Kept
     for cloud/data (`ProxmoxComputeProvider`). Added to `KNOWN_GAPS` and to `MetricRegistry::REGISTRY['vcpu']`
     (status flipped to `GAP`, same pattern).
4. **MEDIUM (QA)** — a numeric promise stored as a numeric string (`"500"`) skipped the registry entirely (only
   `is_int()`/`is_float()` routed a value through `MetricRegistry::isKept()`); it fell through to the text-scan rule
   meant for capability flags, and a key whose bare word happens to appear elsewhere in the codebase (e.g.
   `aliases`, also an unrelated feature-flag key in `ServiceFeatures.php`) would have passed. **Resolution:** the
   check is now `is_numeric($value)`. Test: `it('routes a numeric-string promise through the registry exactly like
   an int, not the text scan')`, which first proves `readInSource()` still contains `'aliases'` (the old rule's false
   "read"), then proves a numeric-string `aliases` promise is caught. **Catalogue impact: none** — `CatalogSeeder`
   stores every numeric entitlement as a real PHP int/float today; no plan on sale changed gap status because of
   this fix.
5. **NOTE (security)** — `Doctor.php`'s comment on the "the metering gap ratchet is not growing" row claimed it
   caught "a fixed gap left on the list"; the code (`array_diff($actualGaps, $knownGaps)`) only ever catches a *new*
   gap. **Resolution:** comment corrected to say the row only catches new gaps, and that the shrink side (a gap
   fixed but left on the ratchet) is caught instead by the Pest test that compares the two lists for an exact match.
6. **LOW (reviewer)** — `MetricRegistry`'s public `keys()`, `status()`, `gapKeys()` were unused. **Resolution:**
   removed; kept `get()` (used by the new KNOWN_GAPS↔registry test) and `isKept()` (used by `PlanPromises` and the
   family-scoping tests).

**Final `KNOWN_GAPS` count: 15** (13 from the first pass + `backup_days` + `vcpu`, both found by family scoping —
see item 3 above).
