## Objective

A VAT number a customer gave is checked in the EU register (VIES) and the answer is kept as evidence; reverse charge applies only to an EU business customer of another member state whose number VIES confirmed (at most 30 days ago), otherwise destination VAT with a review flag.

**WP A (this commit):** VIES behind a provider contract, the recorded check on organizations (migration 000880), when checks run (queue after the number is set/changed, operator command, default-off monthly re-check), the event `tax.vat_number.checked` with notifications, and four doctor rows. The tax decision itself (quote/checkout/renewal/invoice, review flag, staff override, partner self-billing) is WP B; public copy, runbook and provider doc are WP C.

**WP B (second commit):** the tax decision uses the recorded check. Every tax input is built by `VatStanding::taxCustomer()` (quote, cart, guest checkout, staff quote/assisted order, renewals, rated usage, domain renewal, SLA credit, marketplace, work offers, archive fee, wallet forecast, receipts, smoke order). Reverse charge applies only to a business of another EU state whose number was VIES-valid at most 30 days before the quote or issue, or when a staff override is in force. Otherwise the customer pays today's destination VAT, plus a `vat_review` flag when a VAT ID was given. The order and the document keep the check they were decided on: both VAT IDs and the consultation number are printed under the reverse-charge legend. Finance can override the status by hand (CRITICAL: step-up + four eyes, 1–30 days, evidence kept). Partner self-billing VAT comes from the same standing, at the `standard_rates` rate.

**WP C (third commit):** the public promise is true and written down. The knowledge-base article *Firemní faktury, DPH a kredit* (`faktury-dph`) keeps its promise word for word and gains one qualifier in cs and en (content data only: `database/seeders/data/prototype-content.json`): until the VAT ID is verified in VIES, the customer's country's VAT is charged. `VatPromiseTest` pins the text and that the code keeps it once VIES is on. New runbook `docs/runbooks/vat-and-vies.md`, new provider doc `docs/provider-adapters/vies.md` (+ README row), and the go-live row for tax/VIES.

## Security considerations

WP A: RecordVatCheckCommand is system-only (a customer or staff actor is refused 403 `system_only`), so nobody can declare their own number valid; it carries no permission and NORMAL risk because it only records what the register answered. The VIES answer names the trader: `secretResponse` keeps it out of provider_calls, the name/address are stripped from the command audit (AUDIT_STRIP) and never enter the event (only country + last three characters). The endpoint comes from config, not from users. No HTTP call inside a bus transaction (row lock never waits for VIES). Needs onhost-security and onhost-qa review (money + outbound HTTP).

## Migration considerations

000880 adds nullable columns and one index; no data UPDATE (critic item 1: a mass write to existing customer rows). Old code ignores the columns. Legacy rows (vat_status_source NULL) keep today’s money: stored `valid` stays effective valid with reason `legacy_unverified`, stored `payer` stays a VAT payer for self-billing, any other non-vocabulary value reads as `unknown` — until `onhost:vat:verify --apply`. Width note: `vat_checked_number` and `vat_validations.vat_id` are 20; a 19–20 digit unprefixed number (22 with the country) is skipped, never stored.

## Rollback

WP A: set `ONHOST_VIES_ENABLED=false` (the default) — no check runs and every number is charged as before; revert the commit and roll back 000880 (`down()` drops the added columns and the index). Recorded vat_validations rows are evidence and harmless to keep.
