## Context

`docs/proposals/metering-after-launch.md` §2 (M1). ISPConfig keeps aliases, forwards, alias domains and the catch-all in one
table (`mail_forwarding.type` enum alias|aliasdomain|forward|catchall) and `mail_alias_get`/`mail_forward_get` go through
`remoting_lib::getDataRecord`, which filters by the given columns only — so `source LIKE %@domain` returns every kind
(source read from the ISPConfig 3 code, mirror `cyberkathosting/ispconfig3`: `remote.d/mail.inc.php`, `mail_alias.tform.php`,
`remoting_lib.inc.php`, `install/sql/ispconfig3.sql`). The stateful e2e fake filtered by type, which hid this.

## Security considerations (self-review, ecc:security-reviewer style)

- The count runs before the panel write and before the operation is queued; the queued step counts again (`_limit`) when the
  panel was away (H02) — same path as mailboxes, now over `listAliases()` filtered by type.
- `alias.delete` names a remote id: `OWN_MAIL_TARGETS` resolves it against `listAliases()`; filtering by type narrows what a
  customer can delete through it (a forward or catch-all id is refused). No widening anywhere.
- Rows without a `type` keep the old behaviour (counted as alias / forward); real ISPConfig always returns the column.
- No secret, payload or vendor name reaches logs or responses (the error says "the plan allows N of these").
