## Objective

A game server's Pterodactyl panel user is always its own organization's: it is found only by the organization id, never by
an e-mail a customer typed, and the panel password, the panel account view and new collaborators are refused on a server
whose panel user is not the service's organization's. Legacy mismatches are listed for an operator, never re-homed
automatically.

## Context

Permission program (scratchpad `permission-program.md`) P0-02, immediate fix IF-6, decision D12, rulings 9/23/34, exploit
PA-01 (CRITICAL), owner default O2. Evidence: `ProvisionGameServerWorkflow.php:52,56` took the first
`GET /api/application/users?filter[email]=<billing_email>` hit; `billing_email` is customer-set. An organization that wrote a
stranger's address got its server under the stranger's panel user; `panel.password` then reset the stranger's password and
opened every server of that account. `GameMigrationWorkflow` (cross-panel move) called the same `ensureUser()`.

## Security considerations

Closes PA-01 (cross-tenant takeover of a panel account). Identity is the panel's own answer compared byte-for-byte with
`services.organization_id` read live (a moved service does not inherit the old organization's panel account); a missing
service or ref without service fails closed. Refusal messages name no foreign id or e-mail. Deleting sub-users is not gated
(revocation must never be held up). Synthetic e-mails mean the panel's "forgot password" reaches nobody for new users;
the platform's owner-only `panel.password` (HIGH, step-up) is the way in.

## Migration considerations

None (no schema). Existing panel users are not changed (O2). Existing legitimate services: the platform always created
users with `external_id = organization id`, so their repeat orders find the same user by id and nothing changes.

## Review round 1 — findings and resolutions

1. **security MEDIUM — owner taken from the cached binding `meta.user_id`, not the panel's live `servers/{id}.user`.**
   Confirmed, and it is worse than "fails closed" in one direction: a server moved on the panel to a stranger's account while
   the binding still names the organization's user passed the check, so `createSubuser` added a collaborator to a server
   that now sits under somebody else's account (red below). **Resolved** (the reviewer's first resolution): new private
   `ownerIdentity()` reads the live `GET servers/{id}.user` every time and judges that user; when the binding's recorded
   owner differs, the verdict is the new `PanelIdentity::MOVED` (refused with its own message, both ids kept in
   `recordedUserId` for the dry run, never in the customer message). `serverUserId()` (meta first) is removed.
   Why refuse on a disagreement instead of silently following the panel: `GameMigrationWorkflow:182` (a same-panel move)
   still creates the new server under `meta.user_id` / `game_servers.ptero_user_id`; acting while they disagree would leave
   the next migration to put the server back under the recorded user without anybody noticing. The triage step is
   therefore "move in the panel AND make the platform's record name that user" (handoff runbook; a supported CommandBus
   tool for that record is a follow-up — see handoff Concerns), and the dry run shows `moved` with `N (platforma: M)`.
2. **security MEDIUM — past hijacks keep their access; the dry run does not show past `panel.password`/`subuser.create`.**
   Partly in scope. **Resolved in this task's files:** the dry run has a new column `dříve přes platformu` — the succeeded
   `panel.password` / `subuser.create` operations of each service (from `operations.desired->action`, state SUCCEEDED; a
   failed/refused one changed nothing and is not counted), and prints the next step for foreign/unmarked rows (rotate that
   panel account's password after contacting its owner, remove collaborators added through the platform). **Out of scope,
   recorded:** rotating a victim's password / removing sub-users is a write on a stranger's panel account that needs contact
   with its owner (owner rule: no mass change; program ruling 34) — it belongs to the TASK-0038 look-back and the breach
   runbook (`docs/runbooks/breach-register.md`, TASK-0038's file); the handoff asks the integrator to add the step there.
   The operations table is the only record read (the audit log is TASK-0038's); if operations were pruned the column
   under-reports — stated in the handoff.
3. **qa MEDIUM — no test that a 5xx during the external-id lookup propagates.** Not a bug (the code rethrows everything but
   NOT_FOUND); coverage added: `propagates a panel 5xx during the external-id lookup instead of creating a duplicate user`
   (asserts a retryable non-NOT_FOUND `ProviderException`, no POST). Mutation proof: with the catch changed to
   `if (true) return null;` the test fails (`Expecting null not to be null`), restored → green.
4. **qa MEDIUM — no dry-run test for the MISSING verdict and the per-row `unreadable` catch.** Not a bug; coverage added:
   `keeps listing every server when one panel user is gone and another server cannot be read, and shows past credential
   actions` (owned + missing + unreadable (users/14 → 500) + foreign rows in one run, no writes). Mutation proof: with the
   command's `catch (Throwable)` narrowed to another class, the test errors with the uncaught `TRANSIENT`; restored → green.
