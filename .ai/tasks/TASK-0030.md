## Objective

An API token never opens a console, runs a command or adds an SSH key unless the customer issued it with the new
scope `services:console` on purpose; a HIGH action through a token is always refused; a `svc_console` guest gets the
console the role promises.

### WP-A (onhost-security): explicit token scope map, services:console, console-token route and UI, console-token resource scope

Outcome: the permission → token-scope decision is ONE explicit, deny-by-default map
(`domains/Identity/Authorization/TokenScopes.php`); `services:console` gates the console token, command.run/command.send and
shell.*; a token session never holds a step-up; IssueConsoleTokenCommand is decided on the service (resource scope).

### WP-B (onhost-security): fresh step-up for staff writes that check a HIGH permission outside the bus

Outcome: `ApiContext::authorizeAction()` — authorize() plus, for a HIGH permission, the same fresh step-up the bus asks
for (same `step_up_required` answer the console's dialog repeats the request on). Used by POST /v1/staff/dunning/run,
POST /v1/staff/capacity/forecast/run and GET /v1/staff/services/{id}/panel-login (D-10). Reads keep authorize().

## Context

Audit C13-H2c: `ApiContext::assertTokenScope` decided by prefix, so every `service.*` permission that was not
manage/delete fell to `services:read` — a read-only token got a noVNC console (`GET /v1/services/{id}/console-token`) and
the portal's "operate services" preset (read + power) ran commands and added SSH keys. `StepUpService::activeGrant`
matched session-less grants for token sessions. `IssueConsoleTokenCommand` used the organization scope, so a `svc_console`
guest (resource binding) was refused (audit §4).

D-4 check (WP-A): commands whose `permission()` returns null — `CreateOrganizationCommand` (route family `organizations`,
closed to tokens) and `AnnounceDiskTotalCommand` (console command only). None is dispatched from a token-reachable family
(services, invoices, documents, wallet, tickets, dns, zones, domains). VERIFIED by grep.

WP-B: `ApiContext::authorize()` never looked at the permission's risk (audit §4 "Step-up is not enforced on non-bus
staff triggers"). Every `->authorize()` with a HIGH/CRITICAL permission was classified: three non-bus writes
(ReportController::runDunning, ProvisioningController::runCapacityForecast, WebToolsController::panelLogin), the rest
are reads or a check in front of a bus command (OrganizationCommand, ServiceAccessCommand, WithdrawalCommand,
RegistrarConnectionCommand, CatalogCommand, StaffCustomerCommand). The staff console calls dunning/run and forecast/run
through window.OnhostApi; onhost-session-bridge.js opens the step-up dialog on any 403 `step_up_required` and repeats
the request (any method, so GET panel-login too — VERIFIED by reading `call()`); IdempotencyKey never stores a 403.
tests/e2e/*.spec.js call none of the three endpoints (grep). No UI calls panel-login.
