## Security considerations

Self-review in the style of ecc:security-reviewer (backups):
- The dump is the whole database: export writes with `fopen(x)` (no overwrite, no planted symlink), chmod 0600 before the first byte, into a root-made 0700 work dir owned by the run user; the work dir is removed by a trap on every exit.
- Set names are validated (`platform-backups/<Ymd-His>`): no path out of the backup prefix (test).
- The site's PHP never runs as root (setpriv/setsid/env -i, stdin /dev/null, terminal kept from children — the deployer's rules).
- **A planted dump**: the application (www) writes the backups, so a compromised site could plant a dump. The drill refuses a superuser or a member of `pg_execute_server_program`/`pg_*_server_files` and needs CREATEDB: restored by a plain role (the application's own) it gains nothing it did not have. CI proves the refusal (exit 2, nothing created).
- The PostgreSQL password is only in the operator's shell (`read -rs`), never in a file, argument or output; the verdict holds counts only.
- The drill database name is validated (`onhost_drill_<digits>`), the drill never touches the live database; `dropdb` on every failure path (CI checks no `onhost_drill_%` remains).
- One drill at a time (`flock`). No new HTTP route, no customer input. Verdict: no finding open.
