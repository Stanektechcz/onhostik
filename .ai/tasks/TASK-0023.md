## Objective

What outcome the user gets, in one or two sentences.

### Package placement-capacity (decisions 7 and 19)

A plan that sells dedicated PHP workers on an ISPConfig product (web-hosting/profi) can only be placed, pinned, scheduled,
sold and plan-changed onto ISPConfig (a PHP-FPM pool per site); every other web/managed plan says "Sdílené PHP workery".
Node capacity is judged per dimension (disk sold, RAM/CPU measured) with the disk switch off until an operator has read
the read-only `onhost:capacity:basis` report; web and managed orders are judged in the cart like servers. Nothing that
already runs is moved.

### Package metering-core (decisions 9 and 12)

Every usage reading is kept as a sample (`service_usage_samples`); a number the panel could not give is stored as
nothing (null, quality `unavailable`), never as 0, so a failed reading no longer reads "0 %, fine". Raw samples roll into
days and months and are kept 45 days / 400 days / for ever. With the default-off rule `usage.rotation` the watch goes
round every service (managed databases included) instead of the first 200; a first reading is only a baseline, new
metrics are observed until the operator enables them, soft limits only notify, nothing is ever billed from a sample.

- HIGH (owner decision) `domains/Provisioning/Scheduling/PlacementRules.php` — eshop/shop-peak keeps selling "24 PHP workerů (dedikované)" on aaPanel, where one pool per PHP version serves the whole node; moving it to ISPConfig would break its WAF `pro` rate limit and the client-wide `sites` count (see Context). Reported by doctor/report, not fixed. Options: a new shop-peak plan version without the dedicated claim, or ISPConfig rate limiting + `ClientAllowance` counting a site for plans without `sites`, then extend `DEDICATED_PHP_PROVIDERS` logic to managed.
- MEDIUM (ratchet honesty) `domains/Catalog/PlanPromises.php` — `php_workers_dedicated` left `KNOWN_GAPS` because `PlacementRules` now reads it (boolean keys use the text scan, which the ratchet test enforces); the key is kept for family web only. The managed-family gap is recorded in the `MetricRegistry` row's `reason` and in the doctor WARN row, not in the ratchet. A future change could route boolean keys that have a registry row through `MetricRegistry::isKept($key, $family)`.
- LOW `domains/Services/Web/ClientAllowance.php:32` — latent, pre-existing: a managed plan without `sites` placed on ISPConfig (possible today via a staff placement) adds no site to the client-wide `limit_web_domain`. Not changed here (not needed by this package).
- NOTE pre-existing, not fixed: `sellableCapacity()`/`CapacityForecast` read state `drain` while nodes are written `draining`.

### Package metering-core (self-found, open for the owner/reviewers)

- MEDIUM (behaviour, accepted by the orchestrator) `domains/Services/UsageWatch.php` — for every existing service a panel number that is not reported now yields `tags.usage.unavailable` and, when nothing limited came back, `level = unknown` (was 0 % / `ok`); a failed reading no longer resets `notified_level`. Reaches all services on deploy without a switch (truthful direction). ISPConfig servers without the traffic-quota function will show `unavailable.traffic` on web services that sell traffic.
- MEDIUM `domains/Services/UsageWatch.php` — when all limited readings of a service come back null (not an exception), `metrics` becomes `[]`, so `UsageGuard` stops blocking at once (same as before: the old 0 % released it too). An exception keeps the old tags (the guard decays after 26 h, as before).
- MEDIUM (interpretation, ASSUMED) the baseline rule is applied to `UsageGuard` too (plan finding 2 speaks of the upgrade only): the first reading of a newly visited service (e.g. services 201+ once rotation is on) never blocks; services measured before deploy keep their metrics and are not a baseline.
- LOW `providers/Pterodactyl/PterodactylGameProvider.php:325` — pre-existing: casts a missing `disk_bytes`/`memory_bytes` to 0, so a game server's missing number is still "measured 0" (adapter not changed here; phase 3).
- LOW `providers/IspConfig/IspConfigTools.php:386` — pre-existing: swallows `ProviderException` into nulls, so the recorded reason is `not_reported`, not the real fault (phase 3).
- NOTE soft limits: no metric the watch measures is soft today (all five map to `hard` registry rows); `UsageMetrics::notifies()` vs `drivesConsequences()` is the gate that applies once a row is soft.
- NOTE the `onhost:services:usage-watch` closure still prints a 5-column header while the result has more keys (pre-existing; not changed, hot append-only file).
- NOTE rotation on + `--limit`: the per-run batch is `max(limit, ceil(eligible / 24))`, so at ~5000 services each hourly run reads ~210 panels (aaPanel `du`/`find` up to 120 s each) — review the run time with the preview before switching on.
