## Objective

What outcome the user gets, in one or two sentences.

### Package placement-capacity (decisions 7 and 19)

A plan that sells dedicated PHP workers on an ISPConfig product (web-hosting/profi) can only be placed, pinned, scheduled,
sold and plan-changed onto ISPConfig (a PHP-FPM pool per site); every other web/managed plan says "Sdílené PHP workery".
Node capacity is judged per dimension (disk sold, RAM/CPU measured) with the disk switch off until an operator has read
the read-only `onhost:capacity:basis` report; web and managed orders are judged in the cart like servers. Nothing that
already runs is moved.

### Package metering-core (decisions 9 and 12)

Every usage reading is kept as a sample (`service_usage_samples`); a number the panel could not give is stored as
nothing (null, quality `unavailable`), never as 0, so a failed reading no longer reads "0 %, fine". Raw samples roll into
days and months and are kept 45 days / 400 days / for ever. With the default-off rule `usage.rotation` the watch goes
round every service (managed databases included) instead of the first 200; a first reading is only a baseline, new
metrics are observed until the operator enables them, soft limits only notify, nothing is ever billed from a sample.

### Package web-disk-total (decision 10)

A web plan's space is sold as "files, databases and mail together"; the platform now adds the three up (the paying
service plus the further sites its plan carries, never its test copy) and shows the total at once in the summary, the
quota listing, the usage API and the panel quota tab. A part a panel cannot give is null with a reason, never 0. The total
counts against the plan (UsageGuard, PlanFit, level, notice, automatic upgrade) only from the date the operator sets and
only for a service that was told in time (or was ordered after that date); nothing a customer sees in their limits changes
before it. The usage API no longer shows an aaPanel node's whole-node figures as the customer's usage (H286).
