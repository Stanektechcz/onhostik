## Security considerations

- Shadow before enforce: nothing a member of staff does today is refused by the Authorizer part (switch off); what would be
  refused is written down. The is_staff shortcuts, the token view and the panel login are pure security fixes and apply at once.
- The one-time panel link never enters the bus replay store, the audit or the outbox (parked 60 s under a random handle, taken
  once by the controller; test asserts it is absent from `audit_events`, `outbox_messages`, `idempotency_keys`). Review round 2:
  that claim was false for a request WITH an `Idempotency-Key` — the HTTP idempotency middleware stored the whole 200 body (the
  link) for 24 h and replayed it without the bus; the POST route now opts out of that middleware, the answer is `no-store`.
- Eligibility of a panel login is checked before the bus opens an approval request (nobody is asked to approve a sign-on that
  could never happen) and again in the handler.
- Consent seam: only `meta.support_access` by a current member who holds `service.console` and is no staff account counts; no
  staff path writes ticket meta. A ticket counts only when its author is no staff account (D7: never self-satisfiable).
- Consent is read twice — by the bus (`requiresApproval`) and by the handler. If it is gone by the handler, the handler refuses
  unless the bus consumed a second person or the solo waiver for this run. The mirror (approved first, consent added before the
  repeat) is accepted: the repeat runs as consented and the approval stays unspent (it expires).
- Staff mode of a queued run: `desired.staff_mode` is written only by `OperationService::start` from the starting context
  (`StaffActor::acts`); the runner rebuilds `staffMode` from it and StaffActor re-checks the account (staff, active) at every use.
  Deploy note: a staff suspend queued by the pre-TASK-0039 code and settled after the deploy carries no `staff_mode` and settles
  as the customer's pause — deploy with the provisioning queue drained of staff `suspend` runs (they take seconds).
- `token:<id>` sessions: a non-numeric id is never sent to the bigint key (PostgreSQL 500), expired/revoked tokens decide nothing.
- Token of a queued run (review round 2): `desired.token_id` is written only by `OperationService::start` from the starting
  context; the runner re-attaches the token before each privileged step (`IdentityCommandAuthorizer::asToken`) and carries
  `token:<id>` as the run actor's session, so a chained command or run started from a step keeps the token view (and a step-up
  check never falls back to a session-less grant). A run whose `token_id` was scrubbed or is unreadable stops (fail closed).
  Deploy note: runs queued with a token before the deploy carry no `token_id` and finish on the person's view, as before.
- Web entry points (review round 3): `auth:sanctum` accepts a bearer token on web routes too (Sanctum's guard tries the session,
  then the token). Those routes are the browser's (a script tag, a page, the portal's own pre-flight), so they refuse every token
  instead of teaching each controller the token view; `token.scope` is the one place, and a route-table test fails for any
  future `auth:sanctum` route without it. Signed download links (`archiv/…`, `export/…`, `calendar/…`) use no guard at all.
- Shadow log (review round 2): written after the caller's transaction ends, committed or rolled back — never inside it, so a
  failing insert cannot abort a PostgreSQL transaction and a refusal cannot erase the row while the day stays marked.
