## Objective

The operator can answer one question for each permission hole Phase 0 closes: did anybody use it before it was
closed? The operator runs one read-only command that reports, per verified exploit, the sources it checked, the hits and
the unknowns. A runbook says how to record the findings, and says that GDPR notices are drafted but never sent
without the owner.

## Context

Permission program key P0-01 / IF-0, decision D16 (forensic look-back before go-live). §10 O3: notification is the
owner's decision. It covers the exploits of program §9: TD-1 (owner demotes themselves through an invitation), PA-01
(Pterodactyl user of another organization), G1 (Discord after member removal), PA-02 (aaPanel file paths outside the
site root), PA-04 (token session of another organization), SS-1/SS-5 with EXPL-1..3 (staff force-purge or hold lift

an invitation, which discloses the person's e-mail; program §1 and §9, closed by IF-2) and TD-3 (project roles past
`mayGrant`, IF-3): D16 names five exploits, but §1 and §9 list these two as exploitable today too. Style template: `onhost:audit:provider-calls`
(TASK-0005).

## Contracts affected

- New console command `onhost:forensics:lookback {--since=} {--until=} {--source=*} {--json}`. Exit codes: 0 when
  there are no hits, 1 when there are hits, 2 for bad options.
- JSON report shape: `command, generated_at, read_only, window, standing_state, summary, coverage, sources[]`. Each
  source has `key, exploit, title, verdict, checked, hits, unknowns, notes, limits`. Confidence is one of `confirmed`,
  `possible`, `attempt` or `use_or_attempt` (review round 1). Nine sources since review round 2
  (`member_without_invitation`, `project_grant_bypass` added).
- No route, event, config key, migration, permission, schedule entry or provider call. No hot file touched.

## Decisions applied

- **D16**: the look-back runs before go-live and covers every verified exploit. Anything the stored data cannot show
  is an explicit unknown with the tool that answers it, never silently clean.
- **§10 O3**: the command decides nothing and sends nothing. The runbook forbids sending an Art. 33/34 notice or
  submitting the `GDPR_72H` timer without the owner's recorded decision.
- Fixed caveats (such as "reads leave no audit row") go into `limits`, so they do not turn every verdict into
  UNKNOWNS. Discord links still open after a removal go into `notes`, because TASK-0035 revokes them.
- Standing state (PA-01, TD-1 current role) is read in full whatever the window is. A membership made before
  `--since` still counts.
- PII minimisation: ids only, IBANs masked to the first 4 and last 4 characters, only the offending cron paths, and
  control/format characters stripped.
- ~~`SET TRANSACTION READ ONLY` was not used, because PostgreSQL refuses it inside a transaction that has already run
  queries.~~ Wrong, corrected in review round 2 (R2-3): PostgreSQL refuses only READ WRITE after the first query;
  READ ONLY is accepted at any point, and inside a savepoint it ends with the savepoint's rollback. The command now
  switches the database to read-only as the first statement after BEGIN (SQLite: `PRAGMA query_only = ON`, reset to
  OFF after the rollback). MySQL takes the mode only before BEGIN, so there the runbook's read-only role stands.

## Security considerations

- The output holds internal ids of customers and staff. The runbook keeps it outside the web root, readable by root
  only, attached by SHA-256 to the cyber incident, and deleted after the review.
- The command has no schedule entry, no route and no event.
