## Objective

A managed database (and a VPS with a backup add-on) that is sold with backups gets scheduled backups with the sold
retention — but only once the owner switches the new automation rule `backups.compute` on. Until then nothing changes
for any service, and a read-only dry run shows the owner whom the rule would touch.

## Security considerations

- Destructive at a provider: deletion only of `kind = scheduled`, unprotected, non-final rows past retention or beyond the
  generation cap, not under legal hold (service or organization), on the service's own instance, whose volid is exactly a
  vzdump/PBS id of the service's own VMID on the instance's `backup_storage`; the adapter then reads the volume and refuses it
  unless unprotected, of that guest and marked with the row's id. Never an unprotect. Anything else is kept with a reason.
- Adoption of a server backup requires this row's marker where the storage reports notes, so an operator's vzdump is never
  adopted (and so never pruned) as ours. The marker cannot be injected through the caller's label (`:` stripped).
- Only platform-provisioned servers (instance + binding) are selected; historical/foreign resources are not looked at.
- The customer schedule endpoint is unchanged: capped by the sold ceiling; for a VPS the ceiling comes from the ACTIVE add-ons'
  own entitlements, and the scheduler caps any stored policy to it.
- No secrets, events or payload keys added.

## Migration considerations

## Rollback

Switch `backups.compute` off → the previous behaviour for servers (backups already made stay; nothing is deleted while off).
Code: revert the commits. With the switch off two behaviour changes remain: the `final` guard in the prune (the scheduler no
longer deletes an unprotected final archive; `FinalArchive::prune()` still does at its retention), and every web/managed/mail
service being visited (OWNER DECISION above). The server backup notes/adoption change applies to manual server backups too.
