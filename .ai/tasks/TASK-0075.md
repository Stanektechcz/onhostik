## Security review round 1 (PR #68) — resolved on this branch

- H1 reservation token: each reservation carries its own random token in `result` (unused by a reservation otherwise; no
  migration). completeHttp/releaseHttp act only `WHERE key, scope, response_status IS NULL AND result = token`; 0 rows → nothing
  written. Window = `onhost.api.idempotency_in_flight_seconds`, else max(600, 2 × max_execution_time + 60), 3600 when PHP sets
  no limit. Expired rows are freed (a reservation past its window, an answer past its day); a request that lost its reservation
  can no longer write. Tests: slow A taken over by B cannot overwrite B, cannot free B's reservation; window is config.
- M1: the normalized query string (`Request::normalizeQueryString`) is part of the hash; DELETE `?force=1` ≠ none, reordered query = same.
- M2: Retry-After = min(60, age/2 + 1) s from the reservation's age; free-on-exception proved through a real route.
- L1: organization read as ApiContext reads it (non-string, e.g. `?organization[]=`, names none) — test.
- L4: key length from `config('onhost.api.idempotency_key_max_length', 200)` (the key is added to config/onhost.php by PR #67).
- After PR #66/#67 merged: `onhost.api.idempotency_in_flight_seconds` (env ONHOST_IDEMPOTENCY_IN_FLIGHT_SECONDS, unset = computed)
  added next to `idempotency_key_max_length` in config/onhost.php; the OpenAPI generator documents Idempotency-Key on DELETE
  too (contract regenerated, `onhost:openapi --check` up to date; OpenApiContractTest asks DELETE as well).
- Follow-up M3 (documented, not done): replay answers return only the stored body with `Content-Type: application/json`;
  the original response headers (Location, Retry-After, custom headers) are not replayed.

## Contracts affected

- `Idempotency-Key` now also on DELETE; key scope = user + API token + organization (`X-Organization`, `?organization=`,
  else the session's chosen one); the organization is part of the request fingerprint.
- New 409 `idempotency_in_progress` (with `Retry-After`) for a duplicate of a running request.
- `status` added to `invalid_idempotency_key` (422), `already_done` (409) and Discord `invalid_signature` (401).
- Provider error bodies: `provider` and the `[provider:CODE]` message prefix only for staff in staff mode.
- Bus key of invoice payment: `invoice.pay:<op>:<invoice id>:<header>`.

## Security considerations

The reservation row holds no body; the secret-shown-once rule is unchanged (completeHttp keeps the marker). The organization
read by the middleware is only a scope discriminator; authorization stays in ApiContext. The staff check for provider names
uses ApiContext::staffMode + StaffActor::account (no new `is_staff` read).

## Migration considerations

None (the `idempotency_keys` (key, scope) unique index already exists; `response_status`/`result` are nullable).

## Rollback

Revert the commit. Finished rows are read by the old code as before. A reservation row in flight at the moment of the
rollback has no status; the old findHttp would answer its replay with an invalid status (a 500) until the row is past its
`expires_at` (at most 10 minutes) — delete `idempotency_keys` rows with `key LIKE 'http:%' AND response_status IS NULL` when rolling back.
