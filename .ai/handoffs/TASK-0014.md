**Outcome.** The platform can no longer take over a historical site, mail domain or database on ISPConfig or aaPanel
(the owner's rule of 2026-09-24), and no mail query can reach every mailbox on the shared mail server any more.

**Files.**

- `providers/IspConfig/IspConfigWebProvider.php` — `provision()` accepts a pre-existing site only when the
  organization's own `onh_…` client owns it (system group `client{N}` or root `/var/www/clients/client{N}/`);
  `createMailDomain()` only when its group is that client's (`client_get_groupid`); `createDatabase()` only when the
  database hangs off this very site. Anything else: `CONFLICT` before a single write. The client is looked up
  read-only (`findClientId`), because `ensureClient` would create one and rewrite its limits. The mail domain now
  carries its lower-case name in the reference, and `mailDomainName()` never lets `'%@'` through.
- `providers/AaPanel/AaPanelWebProvider.php` — a pre-existing site is accepted only with THIS service's remark
  `onhost:<service>` (written by `AddSite` since the first version of the adapter).
- `providers/IspConfig/IspConfigMailTools.php` — the same empty-name refusal for forwards, fetchmail, spam users.
- `domains/Services/Mail/MailDomains.php` — `across()` reads the fallback only when it is a mail domain: a web hosting
  with no mail domain has no mailboxes, it is not read through its site.
- `domains/Services/ServiceFeatures.php` — the panel capability (`mail()` / `mailTools()`) is asked before a mail
  listing, so a panel without mail still answers `feature_unavailable` instead of an empty list.
- `domains/Provisioning/Workflows/ProvisionWebsiteWorkflow.php` — the binding records `provenance: created|recovered`.
- Tests: `tests/Feature/Provisioning/ResourceProvenanceTest.php` (10 cases); two contract fixtures corrected.

**Contracts.** `provision()`, `createMailDomain()`, `createDatabase()` may throw `CONFLICT`; mail references carry
`domain`; binding ownership gains `provenance`. No endpoints, events, schema or config keys.

**Verification.**

- VERIFIED — failing-first: a historical ISPConfig site, a historical ISPConfig mail domain and a historical aaPanel
  site were adopted, and the provisioning saga bound the service to the historical site; the mail queries went out
  as `'%@'`, and the created mail domain's reference had no name.
- VERIFIED — after the fix: all refused before any write, the platform's own resources are still recovered on a
  retry, the queries go out as `'%@shop.cz'`, and with no name nothing is asked at all.
- VERIFIED — gates: Pint clean, Larastan 0 errors, Pest **932 tests / 14 922 assertions** green.
- VERIFIED — the adoption paths were found independently by the investigation workflow's adoption, writes and
  provenance lenses; the `%@` listing by its writes lens, then read by me before acting.
- ASSUMED — `client_get_groupid` exists on the live ISPConfig remote API and aaPanel's `getData&table=sites` returns
  the `ps` column. If either is absent, the platform refuses (the safe side) and only a retry of its own resource
  after a crash would be affected; nothing historical can be adopted either way.
- NOT TESTED — nothing ran against the live panels.
