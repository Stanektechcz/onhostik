## Outcome

Permission program P0-02 / IF-6 / D12 (exploit PA-01). A game panel user is the organization's by its id alone:
`ensureUser()` looks it up only by `GET /api/application/users/external/{organizationId}` and accepts the answer only when
the panel's `external_id` equals the organization id byte for byte and the user is not a root admin; it never searches by
e-mail again, and a new user gets a synthetic e-mail (`org-<id>-<hash>@game-users.onhost.invalid`, owner default O2: new
users only). `panelAccount`, `setPanelPassword` and `createSubuser` re-verify, right before acting, that the server's panel
user carries the service's current `organization_id` (read live from `services`); otherwise they throw a non-retryable
`ProviderException` VALIDATION with no foreign id in the message. `deleteSubuser` is deliberately not gated (a revocation is
never held up). Server adoption (`provision()` → `servers/external/{key}`) also requires the exact external id. New
read-only operator command `onhost:game:panel-identity --dry-run [--instance=]` lists every game server with its verdict
(owned / foreign / unmarked / administrator / missing / moved / unreadable); `--apply` exits 1 — mismatches are re-homed by hand.

Review round 1 (4 MEDIUM, all resolved or recorded — details in the task file): the owner that is re-verified is the
panel's live `servers/{id}.user`, not the binding's cached `meta.user_id` (red: a server moved on the panel to a stranger
still got a new collaborator); a disagreement with the recorded owner is refused as `moved` until the platform's record
names the panel's owner. The dry run gained a look-back column `dříve přes platformu` (succeeded `panel.password` /
`subuser.create` operations per service) and prints the rotation step. Two coverage tests added (5xx during the
external-id lookup; missing + unreadable rows), each with a mutation proof.

## Release notes for existing customers

- Pure security fix, applies directly: a game service whose server sits under a panel user that is not its organization's
  (another organization's = hijack; no external id = a user the platform did not create) can no longer see the panel
  account, set the panel password, or add collaborators; removing collaborators and everything else keeps working. The
  operator lists them with `php artisan onhost:game:panel-identity --dry-run` and re-homes each by hand after triage
  (program ruling 34: not grandfathered, not auto-re-homed).
- Legitimate existing customers are unaffected: the platform always created users with `external_id = organization id`, so
  their next order finds the same user by id. Their panel e-mails are not changed (O2).
- Behaviour change to note: an organization whose earlier server was placed on an *unmarked* user found by e-mail gets a new,
  second panel account on its next order (the old one is not reused). The dry run lists it so an operator can set the
  external id on a genuinely own account first.
- New panel users get a synthetic e-mail; the panel's own "forgot password" does not reach them — customers use the
  platform's owner-only panel password action (HIGH, step-up).
