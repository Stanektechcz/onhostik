## Concerns

- CLOSED at the 0029–0031 integration (a28c103): `PUT /v1/services/{id}/spec` — a `services:power` token could create a
  schedule whose task runs a console command. Each spec step is now judged by TokenScopes and the token's `can()`
  (`ServiceSpecService::tokenMay`, security-boundaries §26): a power token's console step is skipped as
  `token_scope:schedule.create`, a `services:console` token may schedule it, a token session whose token is gone is refused.
  ApiTokenScopeMapTest case 9 has its body and runs.
- CLOSED at the 0029–0031 integration (found in review round 2): the `backup.delete` service action through a
  `services:power` token was queued (202) through `permissionFor`'s default arm. TASK-0029's map makes it `backup.delete`
  with a fresh step-up, which a token never holds: 403 `step_up_required` (case enabled in a28c103).
- Existing customers' tokens: a token issued before this change with "operate services" or "all scopes" loses consoles,
  commands and SSH keys (by design — a security fix, not a mass change). An integration that relied on it gets 403
  `The API token lacks the services:console scope.` and needs a new key with the console ticked. A token that ran HIGH
  actions (terminate, restore) through a session-less grant stops working — no production path creates session-less
  grants for tokens, so this should reach nobody.
- `ApiContext::can()` is token-aware now: a read-only token of a manager no longer sees deploy env values, revealed listings
  or operation secrets. Any read path that used `can()` to decide something other than disclosure would now see `false` for
  a token. By grep, customer-side callers are `ServiceController` (index: the org-wide listing branch — a token without
  `services:read` never reaches it, TokenRouteScope; show/deploy/resources: disclosure of secrets) and
  `WebToolsController` (deploy env values) — all disclosure decisions; the staff callers are behind routes closed to tokens.
- The staff console calls `POST /services/{id}/console-token` too (cookie session, not a token). Whether a staff member gets
  a console is decided by `service.console` exactly as before: the bus asked for it at organization scope, now the
  controller and the bus ask at resource scope, and a global binding covers both (`Authorizer::bindingCovers`). The only
  difference is ordering: a staff member without `service.console` is now refused before the service-state check.

## Release notes for existing customers

- CZ: Konzole, terminál, spouštění příkazů a SSH klíče jsou u API klíčů nově samostatný rozsah `services:console`. Klíče
  vytvořené dříve („provoz služeb“, „všechny rozsahy“) je už neotevřou; kdo je přes API potřebuje, vytvoří nový klíč a
  rozsah zaškrtne. Akce s vyšším rizikem (zrušení služby, obnova zálohy, DNSSEC) přes API klíč neprojdou nikdy — jen v
  portálu s potvrzením. Host s rolí „Služba: konzole“ teď konzoli skutečně dostane. Stažení závěrečného archivu zrušené
  služby jde jen v portálu, ne přes API klíč.
- EN: Consoles, the terminal, running commands and SSH keys are now a scope of their own for API keys
  (`services:console`). Keys created earlier ("operate services", "all scopes") no longer open them; create a new key with
  the scope ticked if an integration needs it. High-risk actions (terminating a service, restoring a backup, DNSSEC) never
  go through an API key — only in the portal with confirmation. A guest with the "Service: console" role now gets the
  console the role promises. Downloading the final archive of a cancelled service works in the portal only, not through
  an API key.
- Staff: running dunning or the capacity pass by hand and signing into a customer's panel ask for a fresh step-up.

### docs/runbooks/security-boundaries.md

§3 "Keys and tokens", after the bullet on route families:

* **What a token may do is one explicit map** (`domains/Identity/Authorization/TokenScopes.php`): one row per catalogue
  permission, the scope that carries it or `null` = not available to tokens; a permission that is not in the map — or a
  command without a permission — is refused to a token. Consoles, the terminal, commands and SSH keys are the scope
  `services:console` (a console is neither a read nor a restart); no preset of the panel's key form carries it, the customer
  ticks it on purpose. `ApiContext::can()` asks the token too, so a read-only token of a manager sees only what a reader sees.
  A new permission gets its token decision in the same commit (ApiTokenScopeMapTest fails otherwise).
  Test: `tests/Feature/Http/ApiTokenScopeMapTest.php`.
* **A token never holds a step-up.** It cannot step up (`/v1/auth/step-up` is closed to tokens) and a grant made without a
  session is not matched for a `token:` session (`StepUpService::activeGrant`), so every HIGH/CRITICAL action through a
  token answers `step_up_required`. A token request is `token:<id>` whatever it carries: an Origin/Referer of a stateful
  domain makes Sanctum start a session for a bearer request, and `ApiContext::sessionId()` asks the token first.
* **A token is asked for what the action does** on `POST /v1/services/{id}/actions` (`permissionFor` → TokenScopes, at the
  route and in the controller): a console command needs `services:console` alone, a restart `services:power`.
* **Archives and dumps are not available to tokens:** `backup.download` (final archive, backup download) is `null` in the
  map. A `services:power` token can still read and write site files one by one (`GET …/files/download` is `service.manage`),
  so a power token is as sensitive as the site's credentials.

§7 (the console-token bullet) replaced by:

* A console token is issued on the service (resource scope: a `svc_console` guest and a project role get it, a `svc_manage`
  guest and a viewer do not) and judged by the service it was issued for; a token with no known owner is nobody's.

New bullet under the step-up rules (§3, "Step-up"):

* **A staff write that does its work outside the bus asks for the step-up itself** (`ApiContext::authorizeAction`): a HIGH
  permission needs the same fresh grant the bus would ask for (403 `step_up_required` → the console's dialog repeats the
  request); a CRITICAL permission there is a programming error (it goes through the bus for the second person). Today:
  `POST /v1/staff/dunning/run`, `POST /v1/staff/capacity/forecast/run`, `GET /v1/staff/services/{id}/panel-login`. Reads
  keep `authorize()`. Every `->authorize()` with a HIGH/CRITICAL permission in `app/Http/Controllers` is classified in
