# Handoff — TASK-0020

```
From / To:        onhost-security → orchestrator
Task / Status:    TASK-0020 / SELF_VERIFIED (package provider-calls-audit)
```

**Outcome.** `php artisan onhost:audit:provider-calls` answers, read-only and from the platform's own logs, whether the
TASK-0005 hole was used before it was closed: for every `service.action` that named an ISPConfig record by id
(`shell.key`, `dbuser.password`, `dbuser.delete` and every mail action of `ServiceActionWorkflow::OWN_MAIL_TARGETS`) it
finds the write the platform sent (tie by attempt time window + same function + same id, because ISPConfig calls carry
`operation_id` NULL), decides whose the record was from logged listings/reads/creations of any age, and grades it
CRITICAL / HIGH / MEDIUM / REVIEW / INFO / CLEAN. It also lists refusals after the fix (probing per actor), writes no
operation explains, and the log coverage per instance. Output: Markdown or JSON, a file on the private local disk
(`reports/…`) or stdout; exit 1 on CRITICAL/HIGH, 2 on bad options. Nothing is written, no panel is called.

  `Storage::disk('local')` under `reports/` or raw stdout.

  write-function map, sys_datalog map, unattributed-write and evidence function lists.

**Concerns.**

- The tie by time can attach a write to the wrong operation on a busy instance; same function + same id make it
  unlikely. `spam.policy` is tied by time only (its write names the spam-filter row, not the mailbox).
- When nothing was sent and the service has resources on several ISPConfig instances, evidence of all of them is
  merged for the id (ids are per instance) — can only affect INFO/HIGH-attempt rows, never an accepted write.
- A platform-made record whose owner can no longer be determined (binding deleted, no name prefix) is REVIEW with
  `owner_service_unknown`, not CRITICAL.
- The report file is confidential (ids, masked addresses); the runbook says to delete it after the review.

**Follow-ups (not in this package).**

1. `deleteDbUser` can never succeed on ISPConfig after TASK-0005: `listDbUsers` lists only users attached to a database,
   so an unattached user gets NOT_FOUND and an attached one CONFLICT (`IspConfigWebProvider.php` listDbUsers/deleteDbUser;
   same listing behind `ServiceService` dbuser params). Needs its own task (onhost-provisioning).
2. `ProviderCallLogger` should fall back to Laravel Context `operation` (set by `OperationRunner`) so ISPConfig calls
   carry `operation_id` — the staff job view (`ProvisioningController`) filters by it and shows no ISPConfig call today.
   Platform-kernel change (onhost-architect review).
3. `provider_calls` retention: the logger docblock promises 90 days and `onhost:provider-calls:prune`, which does not
   exist; nothing prunes. Owner decision + a real prune command.

**Next.** Review chain (onhost-reviewer, onhost-qa, onhost-provisioning, onhost-integration, onhost-performance); then the
