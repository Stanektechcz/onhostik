# Handoff — TASK-0010

From / To:        onhost-security → orchestrator
Task / Status:    TASK-0010 / SELF_VERIFIED

**Outcome.** A suspension the panel only partly carried out is no longer reported as finished. What the panel
refused to switch off — and therefore keeps running on a stopped service — is recorded on the service and said to
the operators. The quarantine case this class exists for (a suspended site going on sending mail from its cron)
can no longer pass silently.

**Files.**

- `domains/Services/SuspensionDepth.php` — `pause()` collects the refusals and returns them as `left` (the same
  shape `resume()` already returned); new `LEFT_TAG = 'suspension_still_running'`. What the panel refused is
  deliberately **not** added to the paused memory: the platform never switched it off, so no resume may switch it
  "back" on.
- `domains/Provisioning/Workflows/ServiceActionWorkflow.php` — `pauseExtrasStep` writes `tags.suspension_still_running`
  (kind → how many) and publishes `service.suspend.incomplete`; `resumeExtrasStep` drops the tag **before** its own
  skip check, so it also goes when the suspension had paused nothing.
- `domains/Notifications/NotificationRouter.php` — the event routed to the operators (`infra`, `/sprava/sluzby`)
  with a sentence that names the kinds and the suspension's reason.
- `docs/architecture/events-catalog.md`, `docs/runbooks/production-readiness-audit.md` (row 97),
  `docs/context/CURRENT_STATE.md`.
- `tests/Feature/Services/SuspensionDepthTest.php` — one new case.

**Contracts.** One new event (`service.suspend.incomplete`, operators only) and one new service tag
(`tags.suspension_still_running`). No endpoints, schema, config keys or provider calls.

**Verification.**

- VERIFIED — failing-first: with the aaPanel fake refusing `set_cron_status` (`{"status": false, …}` → `VALIDATION`)
  the service went SUSPENDED, FTP 31 was switched off, **cron 21 kept running**, and nothing recorded or reported it.
- VERIFIED — after the fix: `tags.suspension_paused` is `['ftp' => ['31']]` (the refused cron is not in it),
  `tags.suspension_still_running` is `['cron' => 1]`, `service.suspend.incomplete` is in the outbox, and after the
  resume the record is gone.
- VERIFIED — gates in this worktree: Pint clean, Larastan 0 errors, Pest **917 tests / 14 868 assertions** green.
- VERIFIED — the design mistake was found by the test, not by hope: parking the residue in `tags.suspension` lost it,
  because `ServiceService::suspensionPatch()` replaces that tag wholesale with the holds when the state is written.
- NOT TESTED — nothing ran against a live aaPanel or ISPConfig instance.

**Concerns.**

1. **Nothing retries a refusal the panel called final.** The operators are told and it is theirs to finish. A
   scheduled re-attempt would be the next step, but it needs a decision about how often a stopped service should
   poke a panel that has said no.
2. **Existing suspended services are not touched** (the standing rule). Services suspended before this change carry
   no record; if one of them still runs a cron, only a staging query would show it. Recorded as a staging check, not
   run from here.
