# Handoff — TASK-0019

Task / Status:    TASK-0019 / SELF_VERIFIED

**Outcome.** Managed databases (`db-s` 14 days, `db-m` 30 days) and VPSs with an active `backup-plus` / `backup-hourly`
add-on can now be backed up on schedule, with the sold retention, and their expired scheduled backups are removed from
the Proxmox backup storage. All of it sits behind the new automation rule **`backups.compute`** (`default_off`): until
staff switch it on, nothing changes for any service. `php artisan onhost:backups:compute-plan` lists, read-only, whom
the rule would touch and whether each Proxmox instance has a `backup_storage`.

**Files.**

- `domains/Provisioning/AutomationLedger.php` — rule `backups.compute` (`command: null`, `switchable`, `default_off`);
  `enabled()` already honours `default_off` via the settings key `automation.enabled` (same as `capacity.auto_order`).
- `domains/Services/ServiceFeatures.php` — `computeBackupSchedule()` (public): data → `backup_days` > 0 (frequency
  `backup_frequency`/daily, generations `backup_generations`/days); cloud → an ACTIVE backup add-on + its policy row, ceiling
  from the add-on's own entitlements (`Addons::backupPolicy`). `backup_schedule` is added to cloud/data features only
  while the rule is on. No `backup_delete` for compute (it would have offered customers the `backup.delete` action).
- `domains/Services/Web/BackupScheduler.php` — compute families in a separate window (own `$limit`, instance + binding
  required) when the rule is on; `scheduleFrom()` extracted; `computePlan()` for the dry run; prune never takes `kind =
  final` (all families) and on servers only `kind = scheduled`; `expireAtProvider()` via `ExpiringBackups` only for a volid
  naming the service's own VMID on its own instance, failures kept as `meta.delete_blocked`.
- Every eligible service is visited per tick: `eligible()` reads services by keyset (`id > last`) in chunks of `--limit`
  (web/managed/mail, then data/cloud under the rule); the old first-100-by-id cap is gone. Idempotency per slot unchanged.
- `routes/console.php` — `onhost:backups:compute-plan {--limit=500}`; `--limit` of both commands documented as the chunk size.
- `tests/Feature/Services/ComputeBackupScheduleTest.php` (new, 12 tests), `docs/runbooks/backups.md` (new section),
  `.ai/tasks/TASK-0019.md`.

**Contracts.** Rule key `backups.compute`; command `onhost:backups:compute-plan`; feature key `backup_schedule` for
data/cloud only while the rule is on (then `PUT /v1/services/{id}/backups/schedule` accepts them); `backups.meta.delete_blocked`.
No endpoint, event, schema, migration or config change.

**Concerns.**

1. A tick now walks every eligible service: on a large platform one run takes longer (still `withoutOverlapping`, every slot
   idempotent). Per-service panel calls are unchanged.
2. The add-ons sell `offsite`; vzdump volumes are not copied off-site. VDS `backup: daily 7d` and the configurator's
   `backup` option are string entitlements nobody schedules.
3. `expireBackup` unprotects before deleting; used only on rows this schedule made (never `protected` in our table).
4. With the rule on, a data/cloud customer sees `backup_schedule` in `GET …/features` and can set it within the ceiling;
   the web panel's schedule form is in the web tools module only.
