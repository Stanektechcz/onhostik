**Outcome.** Managed databases (`db-s` 14 days, `db-m` 30 days) and VPSs with an active `backup-plus` / `backup-hourly`
add-on can now be backed up on schedule, with the sold retention, and their expired scheduled backups are removed from
the Proxmox backup storage — only volumes the platform provably made (marker, own guest, own storage, unprotected). All of
it sits behind the automation rule **`backups.compute`** (`default_off`). Every tick now visits every web/managed/mail
service instead of the first 100 by id — **owner decision before merge**; `php artisan onhost:backups:compute-plan` shows,
read-only, whom the rule would touch and how many web services are newly visited.

**Files.**

- `domains/Provisioning/AutomationLedger.php` — rule `backups.compute` (`command: null`, `switchable`, `default_off`);
  `enabled()` already honours `default_off` via the settings key `automation.enabled` (same as `capacity.auto_order`).
- `domains/Services/ServiceFeatures.php` — `computeBackupSchedule()`: data → `backup_days` > 0; cloud → ACTIVE backup

  `expireAtProvider()` checks the volid exactly (vzdump/PBS regex, own VMID, instance `backup_storage`) and calls

  `deleteRetainedBackup()`: GET the volume's attributes, refuse protected / other guest / missing marker / other storage

**Concerns.**

1. OWNER DECISION: every web/managed/mail service beyond the old first 100 starts getting backups, prunes and off-site copies
   on deploy day; no switch by design. Read the dry run's last line on production first.
2. Server backups made before this change carry no marker, so their volumes are never pruned by retention (kept, with

   `backup` option are string entitlements nobody schedules.
4. A tick walks every eligible service: longer runs on a large platform (still `withoutOverlapping`, slots idempotent).
