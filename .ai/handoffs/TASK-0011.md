# Handoff — TASK-0011

```
From / To:        onhost-integration → orchestrator
Task / Status:    TASK-0011 / SELF_VERIFIED
```

**Outcome.** Deleting a web hosting on ISPConfig now takes the customer's data and their access with it. Until now
it deleted the vhost row and left the databases, the logins that reach them, the FTP and SSH accounts, the cron jobs
and every further host name of the site on a live node.

**Files.**

- `providers/IspConfig/IspConfigWebProvider.php` — new `dropSiteChildren()` (further names → databases → their
  logins → FTP → SSH → cron), `databasesOfLogin()` and a small `listing()` that survives a refused listing.
  `terminate()` runs it **before** `sites_web_domain_delete`, after its existing ownership guards, and also when the
  vhost is already gone (a site deleted in the panel by hand leaves the same children). What could not be removed
  comes back as `data['leftover']`.
- `domains/Provisioning/Workflows/ServiceActionWorkflow.php` — `terminateStep` publishes `service.purge.leftover`.
- `domains/Provisioning/Workflows/WebMigrationWorkflow.php` — the same for the old node after a move; without it the
  step would have reported `source_removed: true` while the customer's data stayed on the node it left.
- `domains/Notifications/NotificationRouter.php`, `docs/architecture/events-catalog.md`,
  `docs/runbooks/production-readiness-audit.md` (row 98), `docs/context/CURRENT_STATE.md`.
- `tests/Contract/IspConfigContractTest.php` — a stateful ISPConfig fake (`ispPanelFake`) and two cases.

**Contracts.** `terminate()`'s result `data` gains an optional `leftover` (kind → ids); new operator event
`service.purge.leftover`. No endpoints, schema or config keys.

**Verification.**

- VERIFIED — failing-first: with a panel holding a database (+ its login), an FTP account, a shell user, a cron job,
  an alias and a subdomain, `terminate()` sent exactly one call and every one of them survived.
- VERIFIED — after the fix: all of them are gone, and in the refusal case the site is still deleted, the database and
  its login stay (the login owns a database, so it is not taken away), and `leftover` names both by id.
- VERIFIED — gates in this worktree: Pint clean, Larastan 0 errors, Pest **919 tests / 14 883 assertions** green.
- ASSUMED — what ISPConfig itself does behind `sites_web_domain_delete` is not established here. The fix does not
  depend on it: every delete is idempotent and scoped by `parent_domain_id`, so if the panel had already removed a
  child the listing is empty and no call is made.
- NOT TESTED — nothing ran against a live ISPConfig instance.

**Concerns.**

1. **Nodes carry what earlier terminations left there.** Nothing sweeps them (the standing rule: existing services
   and customers are not touched). A staging query would find them: web databases, FTP and shell users whose
   `parent_domain_id` no longer matches any `web_domain` row. Operators' work, with an archive already in hand.
2. **A shared database login.** If a login is attached to another site's database it is left in place, on purpose.
   It appears in `leftover` so it is visible rather than silently kept.
