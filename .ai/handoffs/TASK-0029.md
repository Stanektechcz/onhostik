**Outcome.** Every service action asks for its own permission and risk. `ServiceActionCommand::PERMISSIONS` names each of the
132 `ServiceActionWorkflow::ACTIONS` exactly once and has no default: an unmapped action is refused with 422
`service_action_unknown` before anything runs (system actor included). Deleting a copy is its own permission at HIGH with a
fresh step-up; anything that hands out a shell or root is `service.console`; every `DestructivePreview` action is HIGH + step-up.
The secondary gates (spec apply, action hooks, Discord) ask the same map, and delegated access (SSH keys, game sub-users) is
revoked when the console goes.

**WP2 — secondary gates (D29.7).**

- `RevokeDelegatedAccess` keeps SSH keys / game sub-users only for somebody who still holds `service.console` (shared-service
  end and `lostServices`); the `role_changed` pre-filter stays `service.manage`.

## Concerns

- Residual risk, not fixed here: `service.manage` (svc_manage, developer, `services:power` tokens) still reaches code execution
  as the site user through `cron.create`/`cron.update`, `file.save`, `node.create`, file upload and deploy hooks, and inside a
  game container through `gfile.save`/`gfile.upload` (plugin jars, configs) and `variable.set` (egg startup variables);
  `schedule.run` fires an existing schedule, also a console schedule the owner made (the owner's fixed command, not arbitrary).
  The console line covers shells and root, not code execution.
- Residual risk, not fixed here: the console line holds from now on. Console access made before this fix through the old
  `service.manage` default — game sub-users (`subuser.create`), root password / SSH keys (`access.reset`), console-command
  schedules — stays on the panels while its holder keeps only svc_manage; `RevokeDelegatedAccess` acts only on future role or
  share events, so an agency that already used the hole keeps its shell. See Follow-ups.
- decisions_needed: `subuser.create` and a console-command `schedule.create` ask `service.console` but no fresh step-up,
  although both are persistent console grants (a sub-user under another e-mail outlives a revocation; a schedule runs the
  command for ever) — unlike `access.reset` / `rescue.start`. Recommendation: add both to the step-up (both are rare; the
  schedule one payload-aware like the permission). Not a defect against D29.3/D29.5 as decided; the current behaviour is
  pinned in `ServiceActionPermissionMapTest` ('does not yet ask a fresh step-up for a persistent console grant') so that a
  change is a deliberate diff.
- Staff widening at bus level only: `backup_dr_admin` holds `backup.delete`; `infrastructure_admin` / `backup_dr_admin` hold
  `backup.policy.manage`. No current HTTP entry point lets them reach a customer service: over the customer API they are refused (`/v1/services/{id}` asks `service.read` first; proved in
  `ServiceActionRoleMatrixTest`).
- API tokens have no step-up grant: every new step-up action (database.delete, staging.push/delete, archive.restore,
  backup/gbackup/snapshot.delete) is now refused to tokens — intended, but a behaviour change for integrations.
- `monitoring.set` is a dead entry in `ActionHookService::ALLOWED` and `DiscordService::BUTTON_ACTIONS` (not a service action;
  now refused as unknown instead of being attempted).
- `AssistantService.php` is outside the listed owned paths (three-line removal tied to the removed `staging.push` proposal).

## Release notes for existing customers

- Roles are re-seeded on deploy; only the descriptions of `svc_manage` and `svc_console` change.

  and snapshot.delete. API tokens cannot give a step-up, so they are refused these actions.

  staging" button, the assistant's "replace production with staging" proposal and the chat-sentence button ("přenes staging do
  produkce") are gone.

- Staff, bus-level only: `backup_dr_admin` (`backup.delete`) and `infrastructure_admin` / `backup_dr_admin`
  (`backup.policy.manage`) now satisfy the action permission, but no current HTTP entry point lets them reach a customer service
  (proved by `ServiceActionRoleMatrixTest`). Four-eyes for staff deletion of customer copies is a follow-up.

## 26. A service action asks for its own permission

* `ServiceActionCommand::PERMISSIONS` names every `ServiceActionWorkflow::ACTIONS` entry once and has no default: an action
  nobody placed in the map is refused with 422 `service_action_unknown` before anything runs, whoever asks (the system included).
  A default arm had sent 121 of 132 actions to `service.manage` at NORMAL risk (audit C13-H1).
* Deleting a copy is its own permission — `backup.delete` for web/managed/mail sets, `game.manage` for a game backup,
  `compute.vm.delete` for a VM snapshot — at HIGH with a fresh step-up. The catalogue rates `backup.delete` CRITICAL; that stays
  documentation, because the authorizer forces CRITICAL only for staff-audience permissions and customers have no four-eyes
  (D29.2). The day-to-day manager (developer, a `svc_manage` guest, a `services:power` token) cannot thin out the owner's backups.
* Every `DestructivePreview` action is HIGH with a fresh step-up (`archive.restore` was the one restore without it, C13-H1c).
  No service action is CRITICAL; the operator's `mailbox.backup_retention` (`backup.policy.manage`) takes four-eyes only when it
  prunes.
* A copy the platform keeps — protected, the final archive, under a legal hold — is not deleted or unlocked by a service action on
  any panel: 409 `backup_protected` at request, and the run asks again before the panel call.
* Secondary gates ask the same map: spec apply authorizes every step as its own `ServiceActionCommand` and reports a refused step
  in `skipped`; on a token session it skips a console step (`token_scope:`); action hooks and Discord buttons never run an action
  that needs a fresh step-up (a URL or a chat click cannot give one), and refuse an unmapped action. Each run carries the step's
  own permission for the H315 re-check.
* Residual: `service.manage` still reaches code execution as the site user (cron, `file.save`, `node.create`, uploads, deploy
  hooks) and inside a game container (`gfile.save`, `gfile.upload`, `variable.set`); `schedule.run` fires an existing schedule,
  also a console one the owner made. The console line covers shells and root, not code execution.
* Residual: console access made before TASK-0029 through the old default (game sub-users, root password / SSH keys, console
  schedules) stays until an operator command (`--dry-run` by default) lists and revokes it; `RevokeDelegatedAccess` acts only
  on future events. A game sub-user and a console schedule ask `service.console` but no fresh step-up (owner decision open).
