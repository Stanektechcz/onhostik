## Design choices (review these)

- **Lane heartbeat = the worker's `Looping` event**, not a job per lane: a job sent to a lane nobody works (the masked provider
  lanes on a contained staging) would pile up there and flood the lane when it starts. `QueueLaneHeartbeat` (singleton per
  worker process) stamps the cache at most every 30 s per lane; lanes ever seen are remembered in `system_settings`
  (`queue.lane.<lane>`), so a cache flush does not forget a dead lane. Expected set = lanes ever seen; never-seen (masked)
  lanes produce no row; a retired lane: `php artisan onhost:queue:lanes --forget=<lane>` (audited). Stale after 20 min
  (a job may run 15 min, `--timeout=900`). No rows under `sync`. The existing `QueueHeartbeat` job and the aggregate row
  are unchanged.
- **deploy-gate**: the lane rows are liveness rows like the aggregate one (the gate runs while units are drained), so
  `DRAINED_FAMILIES` reports `automation|queue worker alive (<lane>)` instead of judging it. Without that, every staging
  and production release would stop on drained lanes. **This changes `infra/aapanel/deploy-gate.php`, whose sha256 the
  staging release record pins** — TASK-0049 must record the hash of the SHA it deploys.
- **Prefix row** judges `REDIS_PREFIX` only when Redis carries the cache, queue or sessions, and `CACHE_PREFIX` only for a
  cache store other installations can read (redis, memcached, database, dynamodb). Default = empty or Laravel's derived
  value (`<slug(APP_NAME)>-database-`/`-cache-`, the `laravel` and underscore variants).
- **`disabled` refused too** (as instructed) — Findings HIGH-1 in the task file lists what that changes for staff.

## Release notes

- A provider instance can be **contained** (staff console API: `POST /v1/staff/integrations/{instance}/state`
  `{"state":"contained","reason":"…"}`, fresh step-up). Nothing — customer, staff or the platform itself — sends anything
  to a contained or **disabled** panel; its operations wait and continue when the state is lifted; its backups are neither
  made nor pruned. `disabled` instances existing at deploy become untouchable the same way.
- New doctor rows; staging/production need **`REDIS_PREFIX` and `CACHE_PREFIX`** set to values of their own when Redis or a
  shared cache store is used, otherwise the doctor FAILs (a deploy stops: staging via the expected-nonok list, production
  via Accept-Gate).
- Production with `ONHOST_CLAMAV_ENFORCE=true` (default) and no `ONHOST_CLAMAV_HOST` now refuses uploads/downloads that need
  a scan (was: silently unscanned).
- `onhost:queue:lanes` lists the lanes the doctor expects; `--forget=<lane>` for a lane retired on purpose.
- Containing or lifting an instance needs a reason (422 `reason_required`). A run parked behind a containment is looked at
  again after 15 min, then 30, 60 … at most every 6 h; the time it spent parked does not count against its timeouts; the
  doctor names runs parked for more than 7 days (`automation|no operation parked for more than 7 days`, WARN).
- Automatic node ordering (capacity planner) and `onhost:ispconfig:restore-site` do nothing through a contained instance;
  a staff switch of a customer's registrar account never overwrites a containment; an expiring maintenance lock never lifts one.
- **Residual windows (not changed here):** console tokens issued before a containment are still honoured by
  `ConsoleRelayController::resolve` until they expire (the relay talks to the node, not through the registry); WebTools
  uploads (`WebToolsController::upload` / `fileUpload`) are never virus-scanned — pre-existing, unrelated to ClamAV's new
  production default.
