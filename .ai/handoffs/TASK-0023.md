**Outcome.** A plan that sells dedicated PHP workers on an ISPConfig product (web-hosting/profi) can no longer be placed,
pinned, scheduled, sold or plan-changed onto a panel with one PHP pool for the whole node; every other web/managed plan
says "Sdílené PHP workery" on the price list. Node room is judged per dimension (`CapacityBasis`: disk sold / RAM and CPU
measured) with the disk switch **off** (`ONHOST_CAPACITY_DISK_BASIS=measured`) until an operator has read
`php artisan onhost:capacity:basis`; sold disk no longer counts included sites and staging copies twice. Web and managed
cart lines are judged like servers (behind the existing `ONHOST_CAPACITY_GATE`). No running service is moved or changed.

**shop-peak was verified NOT to land cleanly on ISPConfig** and is therefore not restricted: its WAF `pro` level promises
a rate limit ISPConfig does not apply (aaPanel does), `ClientAllowance` does not count a site for a plan without `sites`
(post-payment refusal for an organization with another ISPConfig hosting), and ISPConfig has no site file manager. It is
reported as an undelivered promise by `onhost:doctor` (capacity WARN) and `onhost:capacity:basis`. **Owner decision
needed** (new shop-peak plan version without the dedicated claim, or make ISPConfig fit and extend the rule).

## metering-core (owner decisions 9 and 12)

```
From / To:        onhost-provisioning → orchestrator
Task / Status:    TASK-0023 package metering-core / SELF_VERIFIED (package); task continues (web-disk-total)
Commit:           88f5920 feat(services): keep every usage reading as a sample, null never 0, rotate the watch over every service
```

**Outcome.** Every usage reading the watch takes is kept in `service_usage_samples` (migration `000860`); a number a
panel did not give is stored as nothing (`value` null, quality `unavailable`, reason code), never as 0, so a failed
reading no longer reads "0 %, fine" and a Proxmox VPS is no longer "always 0 % disk". Raw samples roll into day and month
rows (`onhost:metering:rollup`, 00:20) and are pruned by the owner's retention (`onhost:metering:prune`, 04:35: raw 45 d,
daily 400 d, monthly for ever). With the **default-off** rule `usage.rotation` the watch goes round every service,
least recently measured first, with no fixed cap (per-run batch ≥ eligible / 24) and includes managed databases; while
it is off the watch visits exactly the services it visited before. A first reading is only a baseline (notifies, never
blocks, never orders); automatic upgrade needs two critical readings in a row. Metrics new to a family (managed-database
memory/disk) are observed only until `ONHOST_METERING_ENFORCE_NEW_METRICS=true`. Soft limits (`MetricRegistry`
`limit_kind` soft) can only notify. Samples never reach `usage_events`/billing.

`app/Console/Commands/{MeteringRollup,MeteringPrune,MeteringPreview}.php`, `tests/Feature/Services/{UsageSamplesTest,UsageRollupTest}.php`.
