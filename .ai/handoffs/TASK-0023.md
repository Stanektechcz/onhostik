**Outcome.** Every usage reading the watch takes is kept in `service_usage_samples` (migration `000860`); a number a
panel did not give is stored as nothing (`value` null, quality `unavailable`, reason code), never as 0, so a failed
reading no longer reads "0 %, fine" and a Proxmox VPS is no longer "always 0 % disk". Raw samples roll into day and month
rows (`onhost:metering:rollup`, 00:20) and are pruned by the owner's retention (`onhost:metering:prune`, 04:35: raw 45 d,
daily 400 d, monthly for ever). With the **default-off** rule `usage.rotation` the watch goes round every service,
least recently measured first, with no fixed cap (per-run batch ≥ eligible / 24) and includes managed databases; while
it is off the watch visits exactly the services it visited before. A first reading is only a baseline (notifies, never
blocks, never orders); automatic upgrade needs two critical readings in a row. Metrics new to a family (managed-database
memory/disk) are observed only until `ONHOST_METERING_ENFORCE_NEW_METRICS=true`. Soft limits (`MetricRegistry`
`limit_kind` soft) can only notify. Samples never reach `usage_events`/billing.
