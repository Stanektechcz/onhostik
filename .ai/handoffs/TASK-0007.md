**Outcome.** Sharing a service as "Service: manage" no longer hands over a shell. The web terminal, the per-site SSH
accounts and the game console ask for `service.console`, which is what "Service: console" exists to grant.

**Files.**

- `domains/Services/Commands/ServiceActionCommand.php` — `permissionFor()`: `command.run`, `shell.create`,
  `shell.key`, `shell.delete` and `command.send` now map to `service.console`.
- `tests/Feature/Services/ServiceAccessShareTest.php` — two new cases.
- `docs/runbooks/security-boundaries.md` (§20), `docs/runbooks/web-tools.md` (the sentence that said running a command
  and creating a shell account were `service.manage`).

**Contracts.** No endpoint, event, schema or config key changes. The permission **catalogue** is untouched:
`service.console` already existed and is already held by owner, organization admin, developer, cloud operator and game
operator — so no role loses anything it had, and no `AuthorizationSeeder` rerun is needed. The only role affected is
the shared-resource `svc_manage`, which is the point.

**Verification.**

- VERIFIED — failing-first: the new case failed at `permissionFor('command.run')` returning `service.manage`.
- VERIFIED — after the fix: `ServiceAccessShareTest` + `tests/Feature/Identity` 32/32; full suite in this worktree
  **906 tests / 14 827 assertions green**; Larastan 0 errors; Pint clean.
- VERIFIED — the roles were read before the change: only `svc_manage` has `service.manage` without `service.console`.
- ASSUMED — nothing outside the catalogue grants `service.manage` in a way that expects a shell.

**Concerns.**

1. **The audit finding this started from was wrong, and I am recording that.** A six-lens audit reported
   "`command.run` is gated by `service.manage`, not `service.console`" as a critical hole; `docs/runbooks/web-tools.md`
   documented that mapping as deliberate. What is real is narrower and different: the **role descriptions** and the
   catalogue's own H334 comment promise a manage-without-shell role, and the code did not deliver it. Treat the
   remaining audit findings the same way — read them in the code first.
2. `panel.password` (the customer's Pterodactyl account, which reaches the game console through the panel itself) is
   left at `service.manage` + step-up + HIGH risk. Arguably it belongs with the console group; it is an account
   credential rather than a console session, so it is a product decision, not a defect.
3. The audit row and the `CURRENT_STATE.md` entry for this change are **not written**: both files are locked by
   TASK-0006, which is finished and waiting on a human merge (PR #8). They should be added right after it lands.
