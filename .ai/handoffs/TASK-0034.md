## Outcome

- **Archive preflight (applies directly, every node):** every unpack the aaPanel adapter does — `AaPanelTransport::extract`
  (customer extract, import, backup restore, archive restore, migration) and `restoreFromArchive` — is listed on the node
  first (`AaPanelArchivePreflight`). Refused: hardlinks, devices/fifos, absolute names, `..`, anything beneath a symlink
  of the same archive, symlinks in a zip, symlinks whose target leaves the site. In-site symlinks are kept.
- **Staged copy (review round 1, every node):** an archive that lies in the site is opened ONCE by root; the kernel's path
  of that open file must be inside the site, it must be a regular file with one name, and the target folder must resolve
  inside the site; exactly those bytes are copied to `/www/.onhost-stage` (root, 0700), the copy is judged and handed to
  UnZip, then removed. The tenant can no longer swap the archive between check and unpack or point it at a neighbour's
  backup.
- **Temp files (applies directly):** shell output/exit files, download chunks and preflight listings live in
  `/root/.onhost-shell` (0700); archive copies and restore unpacks in `/www/.onhost-stage` (0700) — never `/tmp`.
- **Tenancy switch (behind `--apply`):** `php artisan operator:aapanel:tenancy` (= `onhost:aapanel:tenancy`) dry-runs by
  default; `--apply` closes nodes serving >1 organization via the bus (`instance.upsert`, HIGH, audited);
  `--apply --instance=<key> --force` closes one named node the dry run did not list (one org + historical sites);
  `--reopen --instance=<key>` reverts one. On a closed node: no in-panel file manager, site import, PHP settings,
  one-click apps, new/changed shell cron, cron "run now" (customer-readable refusal); **restores, archive restores and
  migrations onto the node unpack as root only into STAGE_DIR and are streamed into the site as `www`** — no root write
  inside the site (overlay restore; the root `.user.ini` is left alone).
- **Gate fails closed:** an unreadable instance row → TRANSIENT refusal (retry), features off. A staff edit of the
  instance that leaves `tenancy` out keeps it; a change of it is audited (`options_changed`, `tenancy {from,to}`).
- **Pre-existing bugs fixed on the way:** restore unpacked `.tar.gz` backups with `unzip` (always failed); and a failed
  unpack left `src` empty so the root `rsync -a --delete "$src/"` copied `/` into the site (reproduced in bash).

## Release notes for existing customers

- Everyone on aaPanel: an archive whose contents would reach outside the site, or that is a link / second name of
  another file, is no longer unpacked; the operation fails with the reason. Ordinary site archives, including in-site
  links, unpack as before. Restores of `.tar.gz` backups now work (they failed before).
- Customers on an aaPanel server shared with other customers — **only after the operator runs `--apply`, after the dry
  run, the owner's terminal decision and a notice (O1)**: the control panel's file manager, site import, PHP settings,
  one-click apps, new/changed scheduled shell commands and "run now" are no longer available on that server. Restores
  keep working but no longer delete files the backup does not contain. Suggested notice text (no safety claim while the
  terminal is open): "Your web hosting runs on a server shared with other customers. From <date>, files, PHP settings,
  one-click apps and scheduled shell commands can no longer be changed from the control panel on this server; please
  upload files over SFTP/FTP. Existing scheduled jobs keep running and backups can still be restored."

## Concerns

- HIGH (OWNER DECISION before the first `--apply`): terminal (`command.run`), Node.js projects and existing cron jobs run
  code as the shared `www` user, which can read/write every site on the node (CLI PHP ignores `.user.ini`). Closing is one
  `siteFeatures` flag each (`terminal`, `node_projects`). The command prints this on every run.
- MEDIUM (open, program §3): on OPEN nodes `.user.ini` is read/written as root through the panel file API (a planted link
  when it is not immutable) and the panel's root UnZip can still follow a folder link planted between the staging check
  and the unpack. Closed nodes are not affected.
- ASSUMED UnZip accepts a staged `sfile` outside the site: check on the first live extract (a refusal there would show as
  a failed extract/restore, never as a write elsewhere).
