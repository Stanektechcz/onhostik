## Outcome

- **Archive preflight (applies directly, every node):** every unpack the aaPanel adapter does — `AaPanelTransport::extract`
  (customer extract, import, backup restore, archive restore, migration) and `restoreFromArchive` — is listed on the node
  first (`AaPanelArchivePreflight`). Refused: hardlinks, devices/fifos, absolute names, `..`, anything beneath a symlink
  of the same archive, symlinks in a zip, symlinks whose target leaves the site. In-site symlinks are kept. Since round 3
  a link is resolved against the other links of its archive, where it will land (`y -> .` + `x -> y/../other.cz`, loops,
  a backup's `<site>/up -> ../other.cz` once the folder moves up, escaped names — all refused).
- **Staged copy (round 1, every node):** an archive in the site is opened ONCE by root; the kernel's path of that open
  file must be inside the site, it must be a regular file with one name, the target folder must resolve inside the site;
  exactly those bytes are copied to `/www/.onhost-stage` (root, 0700), judged, unpacked, removed.
- **Downloads read a proven copy (round 2, every node):** `download()` no longer reads by name as root. One root step
  opens the file once, proves it lies in the transport root, is regular and has one name (two names only for a file of
  the sites' own users), copies it into `/www/.onhost-stage/get-*`; chunks come from the copy. Closes the read side of
  PA-02 for final archives, staging relays and customer downloads.
- **Temp files (applies directly):** shell output/exit files, download chunks, preflight listings in `/root/.onhost-shell`
  (0700); archive/download copies, uploads and unpacks of a closed node in `/www/.onhost-stage` (0700) — never `/tmp`.
- **Tenancy switch (behind `--apply`):** `php artisan operator:aapanel:tenancy` (= `onhost:aapanel:tenancy`) dry-runs by
  default; `--apply` closes nodes serving >1 organization via the bus (`instance.upsert`, HIGH, audited);
  `--apply --instance=<key> --force` closes one named node the dry run did not list (one org + historical sites);
  `--reopen --instance=<key>` reverts one. The check and the write run under one row lock (round 2).
- **On a closed node:** no in-panel file manager, site import, PHP settings, one-click apps, **git deploy/rollback,
  staging** (round 2), new/changed shell cron, cron "run now" (customer-readable refusal). The site's transport asks the
  gate at EVERY call (round 2): the panel's root file API inside the site is refused (list/read/write/mkdir/rename/copy/
  chmod/archive), also for work queued before `--apply`; **uploads, unpacks, restores and deletes are done by the site's
  own shell user** (`<prefix>ag`) — no root write inside the site, and (round 3) no root `tar -x`/`unzip` at all: root
  hands the judged archive over on the user's stdin, the user unpacks into a fresh 0700 folder in the site
  (`--no-same-owner --no-same-permissions --no-overwrite-dir`) and moves it in. Final archive on termination falls back
  to the panel's own backup. Restores are an overlay; the root `.user.ini` is left alone.
- **`.tar.gz` restores (round 3):** only on a closed node (site-user unpack). On a node nobody closed they stay refused, as
  before the task (they failed with `unzip`), now with the reason and before anything runs; zip restores there are
  unchanged (root unzip into `/www/.onhost-stage`, panel mirror restore — D11).
- **Gate fails closed:** an unreadable instance row → TRANSIENT refusal (retry), features off. A staff edit of the
  instance that leaves `tenancy` out keeps it — merged from the row locked inside the write (round 2, no lost update);
  a change of it is audited (`options_changed`, `tenancy {from,to}`).
- **Pre-existing bugs fixed on the way:** restore unpacked `.tar.gz` with `unzip` (always failed); a failed unpack left
  `src` empty and the root rsync copied `/` into the site. Round 2 (every node): the same-node staging sync handed any
  file a planted link pointed at to the site user (`chown` dereferenced → root on the node) — now `find -execdir chown -h`;
  the deploy prune ran `rm -rf` as root through a `releases` link — now as the site user.
- **Own round-1 bug found in round 2:** the closed-node unpack ran `tar` as `www`, which the node hardening forbids to run
  binaries (exit 126): every restore onto a closed node would have failed. Now the site's shell user (made on demand).

## Release notes for existing customers

- Everyone on aaPanel: an archive whose contents would reach outside the site, or that is a link / second name of
  another file, is no longer unpacked; a file that is a link out of the site, or a second name of a file the site's users
  cannot read, is no longer downloaded. Ordinary archives and files, in-site links included, work as before. Restores of
  `.tar.gz` backups still do not run on a server nobody closed (they failed before; now the customer is told why) — they
  work on a server closed as shared, unpacked by the site's own user.
- Customers on an aaPanel server shared with other customers — **only after the operator runs `--apply`, after the dry
  run, the owner's terminal decision and a notice (O1)**: file manager, site import, PHP settings, one-click apps, git
  deployments, staging copies, new/changed scheduled shell commands and "run now" are no longer available on that server.
  Restores keep working but no longer delete files the backup does not contain. Suggested notice (no safety claim while
  the terminal is open): "Your web hosting runs on a server shared with other customers. From <date>, files, PHP
  settings, one-click apps, git deployments, staging copies and scheduled shell commands can no longer be changed from
  the control panel on this server; please upload files over SFTP/FTP. Existing scheduled jobs keep running and backups
  can still be restored."

## Concerns

- HIGH (OWNER DECISION before the first `--apply`): terminal (`command.run`), Node.js projects and existing cron jobs run
  code as the shared `www` user / group, which can read (and often write) every site on the node. Closing is one
  `siteFeatures` flag each (`terminal`, `node_projects`). The command prints this on every run.
- MEDIUM (open, program §3, OPEN nodes only): the panel's root write/upload/UnZip/Zip/delete inside the site is a race a
  tenant can win; `.user.ini` root I/O; the staging relay uploads to the fixed name `.onhost-sync.tar.gz` as root when
  production and staging sit on different aaPanel instances (a planted link there is not even a race) — follow-up for the
  staging owner (random name or a root-only relay). Closed nodes are not affected.
- LOW (follow-up): FinalArchive/staging could pack straight into a root-only folder instead of into the site (reviewer's
  "better still"); the read is already safe.
- ASSUMED UnZip/upload accept paths in `/www/.onhost-stage`: check on the first live extract/restore on a test node (a
  refusal there shows as a failed operation, never as a write elsewhere).
